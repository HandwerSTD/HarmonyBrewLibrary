# BrewLibrary 项目功能与创新点

> 面向 HarmonyOS PC（2in1）的 Homebrew 软件包生态客户端。
> 本文档是答辩 / 评审场景下的功能与创新点权威汇总，数据口径与 `docs/` 下各专项文档一致。

---

## 1. 项目概述

**BrewLibrary**（bundleName `top.handwer.brewlibrary`）是一个面向 HarmonyOS PC（2in1 设备形态，最小窗口 1080 × 608）的 Homebrew 软件包生态客户端，基于 HarmonyOS 6.1.0（API 23）以纯 ArkTS / ArkUI 原生实现。

Homebrew 是全球最大的开源命令行软件包管理生态（formulae 8,611 + casks 7,745，共 16,356 个软件包），长期服务于 macOS 与 Linux 开发者。**在鸿蒙 PC 之前，这一生态没有任何原生 GUI 客户端**。BrewLibrary 将 Homebrew 生态的目录浏览、离线检索、榜单发现与本机包管理完整迁移到 HarmonyOS 原生体验之上，是**鸿蒙生态首个 Homebrew 软件包浏览器与管理器**，填补了鸿蒙 PC 在开发者基础设施领域的一项空白。

核心数字一览：

| 维度 | 数值 |
|---|---|
| 覆盖软件包 | 16,356 个（formulae 8,611 + casks 7,745，上游真实全量） |
| 自建分类体系 | 8 + 8 共 16 个分类（Formulae 8 类 + Casks 8 类） |
| 榜单 | 6 张，全部设备端现算 |
| 搜索 | 离线全文检索，零网络依赖 |
| 工程规模 | 13 个模块 + 2 个 entry product；核心新增模块约 6,000 行 ArkTS |
| 数据请求 | 全量元数据同步仅 2 次请求 / 7.33 MB（gzip 实测，真机 21.7s） |

## 2. 系统架构

### 2.1 分层设计

应用采用「entry → 业务 UI → 共享业务层 → 通用层」的四层结构，业务代码按页签垂直拆分，横向能力全部下沉：

```
products/pc_acl        entry：PcAbility / 启动页 / 主页面（完整版）
features/
  pcui                 首页框架：侧边栏 + HdsTabs + 页面容器
  commonbusiness       共享 UX 骨架：BaseHomeView / 模糊标题栏 / 返回键
  brewcommon           数据层：HTTP、数据源适配、目录同步、搜索引擎、共享 UI 原子
  brewdiscover         发现页（榜单）
  brewformulae         Formulae 页签
  brewcasks            Casks 页签
  brewdetail           包详情页（formula / cask 共用一路由）
  brewsearch           搜索页
  mine                 「我的」页（含本机包管理）
  pcnative             本机执行能力（NAPI + Shell 工具链）
common                 通用原子：Preference / 路由 / 账号 / 事件
```

三条架构原则贯穿始终：

1. **字段命名保留 Homebrew 原生语义**（`token` / `tap` / `bottle` / `artifacts` / `dependsOn` / `kegOnly` / `installs30d`），上游数据结构变化时解析层零改动；
2. **页签之间零横向依赖**——共享组件收敛到 `brewcommon`，避免复制漂移，也避免 `brewcasks` 依赖 `brewformulae` 这类无语义的依赖方向；
3. **每个页签持有独立 `PageContext`**，页面栈互不串联，二级页通过 `routerMap` 注册（HAR 的 routerMap 本身就是编译入口）。

### 2.2 数据链路

应用不内置任何数据快照（`rawfile/mockdata/` 已整目录删除），数据全部来自现网与设备端：

| 来源 | 用途 | 请求成本 |
|---|---|---|
| formulae.brew.sh（官方上游） | 包详情现网单条、per-token 索引、analytics 安装统计 | 单条 1.7 KB / 按需 |
| harmonybrew.atomgit.com（镜像） | 归一化全量目录 + 统计快照，可切换容灾 | — |
| 全量元数据端点 | 后台同步全量 `desc`，供分类与检索 | **2 次 / 7.33 MB** |
| 设备端 brew 命令 | 本机已安装 / 可升级包 | 本地执行，零网络 |

两条数据方言由统一的适配层（`UpstreamAdapter` / `HarmonybrewAdapter`）抽象，数据源地址与连通性探活结果在「我的」页可视、可切换。

## 3. 功能详述

### 3.1 Discover · 榜单发现（鸿蒙生态首个基于真实安装统计的软件包推荐系统）

Discover 是本项目的算法核心，也是**鸿蒙生态内第一个把软件包「推荐」做成可解释、可溯源数据产品的实现**——它不是运营编辑位，而是一套跑在设备端、以官方安装统计为唯一事实来源的推荐系统。

**六张榜单，全部设备端现算。** 应用内不落任何榜单快照，目录可用时榜单成员由 `BrewCatalogAlgo` 在设备端以官方 analytics 数据实时计算；目录不可用时走空态而非回落旧数据，保证用户看到的永远是算法口径下的真实结果。

**算法口径经过系统性实测校准**，关键设计包括：

- **口径统一**：Formula 严格采用 `install-on-request`（用户主动安装）口径，Cask 采用 `cask-install`。理由经过实测量化——官方 `install` 口径里依赖被动安装占比高达六成（30d 窗口 `install` 1,461 万次 vs `install-on-request` 574 万次，on-request 仅占 39%；`ca-certificates` 被动安装占比 95.0%、`aws-c-cal` 99.6%）。混用口径会推出一张「依赖包榜」而非用户真正想装的工具榜；
- **family 归并**：`python@3.14` / `python@3.12` / `python@3.11` 这类多版本 token 按 family 去重（7,976 → 7,779 个 family），用户要安装的是 family 而非某个版本号；例外表（`@` 后缀非版本号的场景）显式维护；
- **趋势分防炸**：增速 `vel = 30d 量 / 此前 11 个月月均`，对无历史的新包不虚构分母（实测若加 `max(1,·)` 保护，`llvm@22` 的 vel 会炸到 22,636），而是把「没有历史」建模为独立类别（新星榜）；排序分 `score = log1p(vel) × log1p(vol)`，双向 log 压缩保证「涨得快」且「本来就大」的包胜出，排序值永不 cap（实测 vel p99 = 10.0、max = 22,637，cap 会把整张榜压成同一分值）；
- **双口径不混排**：Formula 与 Cask 基数不同（family 7,979 vs 5,799）、口径不同，各自排名后交错展示；
- **算法双实现互验**：同一套口径在设备端（ArkTS）与可执行参照实现（Python）各有一份，配套不变量校验脚本（`check_algo.py`），阈值偏差超过 20% 即报警——阈值漂移是「需要人看一眼」的信号，静默自适应会悄悄改掉榜单语义。

**呈现层**：页面采用「单包大图卡 + 榜卡」混排信息流（2 栏瀑布流），大图卡紧跟它所属的榜卡形成视觉锚点；榜内行展示包名、英文描述与「查看」入口，徽标展示真实倍率（如 ↑10.0×）；每张榜的渐变卡头以代码绘制并带 `sys.symbol` 水印——Homebrew 官方 API 没有任何图标字段，这一设计让纯数据驱动的榜单依然具备强的视觉辨识度。所有上榜条目可直达详情页，**榜单前 N 名 100% 可落地到详情**（路由层以设备端算出的 id 与分类直接派生）。

### 3.2 本机包管理（鸿蒙生态首个直连 brew 工具链的原生 GUI 管理器）

这是本项目技术纵深最大的一块，**也是鸿蒙生态内第一个以原生应用形态打通 Homebrew 本机命令链路的实现**——在此之前，鸿蒙 PC 用户管理 brew 软件包只有终端一条路。

**直连设备端 brew 命令。** 通过自研的 native 执行通道（`features/pcnative`，NAPI + ShellUtils），在应用内执行 `brew info --json=v2 --installed`，把 JSON 输出流式解析归一为 `BrewInstalledPackage[]`。工程细节包括：

- brew 可执行文件按「环境变量 → 固定候选路径」两级发现，执行通道与发现通道共用同一份候选表；
- 结果带进程内新鲜窗口缓存（10 分钟）并落盘快照，重复进入页面零命令执行；
- 失败分六类（找不到 brew / 执行能力不可用 / 超时 / 非零退出 / 输出解析失败 / 形状不符），分类进日志、页面走对应失败态，绝不静默吞错。

**三个集合、一个口径。** 已安装 / 待更新 / 已更新三个集合由唯一入口 `loadSets()` 派生：`outdated` 与 `updated` 均从 `installed` 推导，`updated` 取补集——保证三个集合不重不漏，且「最近更新的排前面」的语义成立（这是先算了数据再定的口径：直接按安装时间倒序会让两张卡片列出同一批包）。

**体验纵深。** 列表页支持按 chip 隐藏「作为依赖安装的包」，聚焦用户主动安装的软件（该判定来自 `install_on_request` 字段，与榜单口径同源）；本机包行直接点进包详情页，`token` / `id` / `categoryKey` 由路由参数统一派生，与目录条目共享同一套详情链路，「同分类其他包」推荐照常可用；自定义 tap 安装的包在数据源无记录时显示「未找到」而非报错。版本号与安装来源的摆位按真实数据长度设计——cask 版本号实测可长至 45 字符（`2026.2.5,262.10315.131 → 2026.2.5,262.10315.132`），因此版本放充裕的副标题行、来源放最短的尾部槽位。

**命令执行闭环。** 包详情页一键生成安装命令并支持终端样式 Sheet 执行；执行 Sheet 收归顶层宿主，结束提示带退出码；设备上找不到 brew 时，「我的」页三块本机包入口整体隐藏，由提示卡引导安装 Harmonybrew；侧边栏 Shell 入口按执行状态显示。

### 3.3 Formulae / Casks · 全量目录浏览

- **全量无裁切**：浏览集覆盖目录全量（真机日志 7,508 formula / 5,548 cask，family 去重后），没有「前 100 包」的硬裁切——这依赖后台全量元数据同步：启动后 2 次请求拉齐 16,356 个包的 `desc`（对比逐条拉取要 16,356 次请求 / 28 MB，全量方案在字节数与请求数两个维度同时更优），流式扫描落盘；
- **自建分类体系**：官方 API 没有任何分类字段，本项目以「策展覆盖 → 关键词词表 → 形态桶 → 兜底」四级判别在设备端现算 8+8 分类，词表由 `lexicon.json` 生成并配套准确率评测（兜底率经三轮优化从 70.6% 降至 48.1%）；
- **三层导航**：分类卡（卡内预览 5 条）→ 分类二级页（chip 筛选 + 全量列表）→ 包详情页，`LazyForEach` 虚拟滚动支撑全量列表流畅渲染；
- **详情页 11 分区**：描述 / 版本 / 依赖 / bottle 标签 / artifacts / caveats / 生命周期（`deprecated` / `disabled` 带日期与替代品跳转警示，这是 Homebrew UX 的刚需）/ 热度等，formula 与 cask 共用同一路由。

### 3.4 Search · 离线全文搜索

- **零依赖纯函数搜索引擎**：对全量包名与描述建立本地索引，词表打分排序，**弱网与离线环境下检索能力完整保留**——这是与「搜索必联网」的常规应用市场产品最本质的差异之一；
- **双入口闭环**：搜索历史（用户真实搜索词，落盘持久化）与搜索发现（设备端目录真实热门词）并列，与榜单、目录共同构成「发现 — 检索 — 安装」完整闭环；
- **显式触发**：搜索以回车 / 点击显式触发，避免输入过程的高频无效计算；
- 引擎配套可执行检查脚本（`check_engine.mjs`），行为回归有保障。

### 3.5 数据源容灾

- 官方上游与 Harmonybrew 镜像两条方言由统一适配层抽象，「用哪个源」与「走不走网络」在架构上彻底分离；
- 数据源地址与连通性探活结果在「我的」页可视、可切换，缓存按源隔离（`BrewSourceCache` / `CacheEpoch` / `CacheAdmin` 职责单一拆分）；
- 取数失败一律走空态 / 失败态，绝无崩溃路径；部分链路保留「上一次成功归一过的详情」作为会话内降级。

### 3.6 「我的」页

华为账号、内容上新、公告等原有能力保留，本机包三块（已安装 / 待更新 / 已更新）与数据源管理、页面区块开关有机融合；所有空态、加载态、失败态齐备。

## 4. 创新点

### 4.1 生态创新：鸿蒙首个 Homebrew 生态客户端

- **首个**将 Homebrew 全量软件包生态（16,356 个包）带入 HarmonyOS PC 的原生应用，对标 macOS 上 Homebrew + GUI 前端（如 Formulae cider 等）的组合形态，在鸿蒙上一次到位；
- **首个**以原生 GUI 形态直连设备端 brew 命令链路的应用：本机包读取、可升级检测、安装命令执行、Shell 入口，覆盖包管理全生命周期；
- 面向鸿蒙 PC 这一新兴设备品类的开发者刚需场景，属于鸿蒙生态的**基础设施型应用**，而非既有品类的移植复刻。

### 4.2 算法创新：设备端现算的可解释推荐

- **推荐算法全部在设备端现算**，无榜单快照、无云端依赖——同类产品市场的「编辑推荐位」模式被替换为「口径透明、数字可溯源」的数据产品：每张榜的窗口起止、总量、阈值都随数据落盘供展示与审计；
- **口径工程**：对官方 analytics 数据的口径陷阱做了系统性实测（多记录求和、千分位字符串、缺失字段、被动安装占比、多版本 family、窗口子集性质），形成一份带实测证据的算法权威文档 + 双实现互验机制，这在应用侧推荐系统中是少见的严谨度；
- **分类现算**：上游无分类字段的前提下，用「词表 + 形态桶」在端侧构建 16 分类体系并随上游自动演进，**新增包无需发版即可出现且分类正确**。

### 4.3 工程创新：端侧数据工程与原生执行通道

- **全量同步替代逐条拉取**：以「2 请求 / 7.33 MB」替代「16,356 请求 / 28 MB」，真机实测 21.7s 完成全量 `desc` 落盘——该方案经过了 6 个候选方案的系统对比（逐条 hydrate、分页按需、Range 分片等均被量化否决），是典型的端侧数据工程决策；
- **NAPI + Shell 的本机执行通道**：在应用沙箱约束内安全地执行设备端命令，失败六分类、快照缓存、新鲜窗口等设计兼顾了健壮性与礼貌性（不给公共源制造 churn）；
- **零内置数据**：应用不携带任何数据快照（历史累计删除 mock 逾 830 KB），体积与数据新鲜度同时受益，取数失败走空态的确定性设计取代了「多数据模式开关」的复杂度。

### 4.4 体验创新：桌面原生范式

- 专为 2in1 大屏设计的三栏布局、侧边栏导航与模糊材质标题栏（HDS `ScrollEffect` 规范的逐场景落地，含标题栏让位三写法的对照实测）；
- 底部悬浮操作栏、终端样式执行 Sheet、chip 筛选等交互均按桌面端习惯设计，最小窗口 1080 × 608 下完整可用；
- 「发现 — 检索 — 安装」全链路离线可用的降级设计：无网时目录、榜单走空态，搜索能力完整保留。

## 6. 质量保障

- **构建期校验**：策展清单校验（`generate.py`，支持联网 / 缓存 / 纯本地三模式）、榜单算法不变量校验（`check_algo.py --fetch`）、搜索引擎可执行检查（`check_engine.mjs`）；
- **字节码级验证**：符号是否真进 ABC、HAR routerMap 是否合并进 HAP，均有脚本化检查项，不止步于 `BUILD SUCCESSFUL`；
- **真机闭环**：全部功能在 HUAWEI MateBook Pro（2in1）真机验证，`devecocli` 驱动构建、装机、日志、UI 布局检查的完整工作流；
- **文档即口径**：算法口径、数据规范、交接说明、踩坑索引均为带实测证据的版本化文档（`docs/` 六篇专项文档），任一结论可回溯到实测数字。

## 7. 一句话总结

**BrewLibrary 把全球最大的开源包管理生态首次带入鸿蒙 PC**：以设备端现算的可解释推荐算法、离线可搜的全文检索、直连 brew 工具链的本机包管理，以及 2 次请求同步 16,356 个包的端侧数据工程，在鸿蒙生态上完成了一套从数据到体验都「原生」的开发者基础设施。
