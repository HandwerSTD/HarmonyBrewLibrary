## 3. X · 远程 brew 控制台（本轮主推）

> **2026-11-22 二次裁定：搁置，随 Mac 迁移叙事同入展望。** Mac 迁移前提失效后，X 的
> 三个锚点经重压均不成立：①Linuxbrew 服务器/NAS——用 brew 管服务器的用户本就是少数，
> 且他们恰是终端原生人群、最不需要 GUI 的那批；②第二台鸿蒙 PC——需求方已裁定太少；
> ③旧 Mac——已入展望。而 X 是全部轮次中成本最高的一条（libssh 交叉编译 + 密钥管理 +
> 主机管理 UI + 攻击面），价值/成本比为管线最差。探针与 spike 取消排期；展望保留——
> 管线对输入来源不敏感，若迁移潮真的到来，「连上旧 Mac」只是 B′ 多一种输入。

**一句话**：内嵌 SSH 客户端（libssh），BrewLibrary 从「本机的包管理器」升级为
「**我的所有跑 brew 的机器**的控制台」——同一套目录 / 详情 / 搜索 / 榜单，inventory
按主机切换。

### 3.1 两个场景锚点

**场景一（最强）：旧 Mac 直连迁移。**
B（迁移工作台）现在的输入方式是「在 Mac 上跑 `brew bundle dump` → 把文本粘进来」——
要求用户在旧机器上开终端、跑命令、倒腾文本，这是 B 最大的摩擦点。有了 SSH 客户端：

> 同一局域网内，BrewLibrary 直接连上旧 Mac（macOS 打开远程登录即可），远端执行
> `brew info --json=v2 --installed`，清单自己过来 → 逐条标注适配态（A）→ 勾选进批量
> 安装队列。

迁移工作台从「复制粘贴」变成「连上旧 Mac」。这正是 motivation.md 里核心用户
（从 Mac 迁来的开发者）的第一天体验，且不需要旧 Mac 装任何东西。

> **2026-11-22 裁定**：Mac 迁移用户群前提不成立（`round6.md` §1），场景一降级为附带
> 可能（并存 ≠ 迁移，有则用之，不作叙事前提）；X 重锚为 Linuxbrew 服务器 / NAS 与
> 第二台鸿蒙 PC，见 `round6.md` §4。

**场景二：远程主机的 brew 管理。**
Linuxbrew 服务器 / NAS / 第二台开发机——现在这些机器的 brew 只有终端一条路。SSH
控制台让「我的」页本机包三块（已装 / 待更新 / 已更新）按主机切换，安装与升级命令落
到选中主机。与 round1 否决的「brew services 服务面板」不冲突：那是否决「把鸿蒙 PC 当
服务器」，本条是「从 PC 管别的机器」。

### 3.2 架构：brew 环境 = 上下文

关键洞察是**命令集完全一致**：远端跑的还是 `brew info --json=v2 --installed` /
`brew outdated --json` / `brew install --dry-run`，输出 JSON 一个字节都不用改解析。
因此：

| 层 | 改动 |
|---|---|
| 数据解析 / 详情页 / 搜索 / 榜单 / 分类 | **零改动**（目录是同一个 Homebrew 目录） |
| 执行通道 | 增加第二传输层：本机（pcnative）/ SSH 远程（libssh NAPI） |
| inventory（已装 / 待更新 / 已更新） | 按主机隔离：主机 chip 切换，缓存按 hostId 分（沿用 `BrewSourceCache` 的按源隔离先例） |
| 执行 Sheet | 指定目标主机；远程安装 / 升级前置 dry-run 预演（复用 round2 J） |

### 3.3 实现路径（实测先行三步）

1. **探针定路径**（一次 TempEnvProbe 实测，`docs/knowledge/2026-11-21-probe-inside-app.md`
   的现成方法）：应用进程内 `command -v ssh` + `ssh -V`。若设备自带可执行 ssh，
   MVP 可以**零原生开发**跑通（`ssh -o BatchMode=yes user@host brew …` + 密钥免口令）；
   若没有或不可执行，才走第 2 步。
2. **libssh NAPI 集成**：照抄 `docs/libgit2-handover.md` 的既定范式——小调用面
   （connect / exec / disconnect + 事件回调）、十类可分辨错误、超时可中止、进度回调。
   libssh 为 LGPL-2.1（随包动态链接 .so + 许可声明合规）；加密后端选 mbedtls 可捆绑，
   OHOS arm64 交叉编译 spike 先行（`features/pcnative` 的 .cxx 工具链是现成底座）。
3. **密钥与信任**：私钥口令 / 密码存 **Asset Store Kit**（关键资产存储——这是 round4
   判据下少数真正通过的鸿蒙特性）；known_hosts 走 TOFU + 首次指纹确认 UI。

### 3.4 安全与边界

- 远程破坏性操作（install / upgrade / uninstall）一律先 dry-run 预演 + 确认，复用 J 的
  交互；执行结果带退出码提示（现有执行 Sheet 语义）。
- **应用不做 SSH server**：控制台是被控端的对立面；PC 被远端管理的场景轮不到应用自己
  开端口。
- pc_normal（无执行能力版本）不提供远程主机功能，与「逛不需要权限、装才需要」的
  双版本价值观一致。

### 3.5 与 W′ 的关系

同一动机（多机互见）的两个机制：**SSH = live 互见**（可达时，直接读远端真实状态）；
**云同步 = 异步兜底**（不可达 / 离线时，只有主动清单的快照）。若 X 落地，W′ 的双机场景
大部分被 live 互见覆盖，W′ 退为离线兜底；若实测发现设备无 ssh 且 libssh 移植成本过高，
W′ 独立成活。**先跑探针再排期。**

### 3.6 手机遥控：留门不立项

需求方提到「手机直接给电脑装软件」——如实拆解：这需要手机端 App（新 product、新 UI），
是独立立项级决策。它与 round1 否决的「手机浏览 brew」不同（遥控器 ≠ 第二块屏，执行体
在 PC），但仍建议**当前不立项**：PC 控制台已覆盖绝大多数时刻，且手机端的成本不是
移植而是新做。留给未来的门：**安装队列落盘为数据而非内存态**（本来批量队列就该持久化，
round2 B 已要求）——未来任何前端（含手机）触发同一队列，零架构改动。

### 3.7 风险清单

| 风险 | 处置 |
|---|---|
| 设备无 ssh 二进制 / 不可从应用进程执行 | 探针先行；fallback 是 libssh 移植 spike 的结论 |
| libssh 交叉编译链（mbedtls）在 OHOS NAPI 的坑 | spike 先行；libgit2 范式降低不确定性，但不为零 |
| 主机可达性（不在同一网段） | 文档引导 Tailscale / 端口转发属于用户侧网络；应用只管连得上之后的体验 |
| 旧 Mac 未开远程登录 | 迁移流程第一屏给「如何开启」引导 |
| 目标机 brew 版本差异 | 命令 JSON 输出向后兼容性好（v2 已冻结多年）；解析层已有容错分类 |

## 4. W′ · 工具清单同步（收窄版）

**一句话**：只同步**主动安装（install-on-request）的库**及其 taps——「换机时，一键复制
你的旧电脑 CLI 环境」「台式机 + 笔记本双机互见」。

- **收窄依据（需求方裁定）**：全量 Brewfile 太庞大且无意义——依赖包不该同步（装 A
  自然带 B），主动清单才是「我的工具链」；口径与 Discover 的 install-on-request、
  「我的」页「隐藏作为依赖安装的包」chip 完全同源，与 Brewfile 语义（`brew bundle dump`
  只 dump 主动安装）天然一致。
- **体积**：KB 级（几百 token + taps 行），同步成本可忽略。
- **两个交互**：
  1. **换机**：新机上打开同步清单 → 逐条标注适配态（A）→ 勾选进批量安装队列（B 的
     队列）；这就是「一键复制 CLI 环境」。
  2. **双机互见**：台式机打开 App 时一张轻量卡「你的笔记本今天新装了 gh、jq」→ 一键
     跟装。把「发现好库」在自己两台机器之间流转（与 round2 C1 新适配速递同一心理模型）。
- **机制分级**：v0 = 文件流（导出到 `Download/<bundleName>/`，经任何渠道自传，零云依赖）；
  v1 = 账号端云同步（默认关、显式开启，沿用 round4 的隐私注记）。
- **与 B 的关系**：W′ 就是 B 导出链路的同步化增强，不新增页面骨架。

## 5. 优先级与实测清单

| 条目 | 强度 | 成本 | 门槛 |
|---|---|---|---|
| X 远程 brew 控制台 | ★★★★★（二次裁定后：搁置入展望） | 中-高 | 原门槛「探针 + libssh spike」取消排期 |
| W′ 收窄版 | ★★★ | 低（v0） | 无门槛，v1 云同步再评估 |
| BYOK 修正落实 | 随 round1 D 系列走 | — | 不新增工作，只改实现路径 |

**先行实测（结论直接决定 X 的路径与排期）**：

1. 应用进程内 ssh 二进制探针（`command -v ssh` / `ssh -V` / BatchMode 连通性）——
   一次 TempEnvProbe 的事；
2. libssh + mbedtls 的 OHOS arm64 NAPI 交叉编译 spike（半天量级，参照 libgit2 流程）。

X 是四轮头脑风暴以来**第一次把「迁移工作台的最大摩擦点」物理消除**的提案：B 的输入
从「人肉搬运文本」变成「连接即读」。若探针与 spike 都通过，建议 X + B + A 三件一起
排期——A 给标注，B 给队列，X 给输入，正好构成 motivation 里「搬得动」的完整闭环。

> **2026-11-22 裁定**：B 的前提失效（`round6.md` §2），排期建议在新叙事下重估为
> **B′（开局套装）+ A + X（服务器锚点）**；「搬得动」改为「管得住」，旧 Mac 直连降为
> 展望能力（管线不变，多一种输入）。
