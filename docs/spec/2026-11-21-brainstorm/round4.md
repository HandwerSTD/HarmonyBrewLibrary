## 1. 判据：鸿蒙特性对 brew 的真正角色

**核心事实**：brew 的使用模型是「不开 App」——用户在终端里干活，不会主动打开一个包管理
App。这意味着鸿蒙特性对 brew 的价值只有一条主线：

> **把 brew 的事实（可升级 / 上榜 / 装好了）和动作（安装 / 升级 / 导入）长到系统界面上，
> 让 brew 的服务不打开 App 也在发生。**

判据：任何特性必须缩短「brew 发生了一件事 / 用户想做一件事」到「完成」的路径。
按此判据，鸿蒙特性分成三类有用 + 一类不做：

| 类 | 特性做的事 | 对 brew 的意义 | 条目归属 |
|---|---|---|---|
| **触达** | 通知 / 服务卡片 / 意图直达 | brew 的事实主动找到用户；用户不逛 App 也被服务 | H（已立项）、U（本轮新增） |
| **入口** | 深链 / 分享卡 / 文件关联 / 快捷方式 / 拖拽 | 用户想做一件事时，入口离得更近 | K / R / S1（已立项）、V（本轮新增） |
| **空间** | 多窗口 / 独立执行窗 | 长任务不打断工作流 | S2（已立项） |
| **记忆** | 账号云同步 | 多台 PC 之间工具清单不丢 | W（本轮新增，可选） |
| 不做 | 一切「为了用特性而用」 | 见 §4 否决清单 | — |

## 2. 对「一多移植手机浏览」的正式回应：同意否决，但有一个例外值得记录

需求方判断：**用一多把浏览功能移植到手机上不值当，谁会在手机上看 brew？**

**结论：同意，维持 round1 §3-4 的否决。** 浏览 / 搜索 / 榜单的消费场景锚定在「坐在电脑
前准备干活的人」，手机上看包列表是伪场景——这个判断与 motivation.md「它的价值集中在
『用电脑做事的人』」的边界声明自洽。

**唯一的例外**：手机在 brew 故事里的真实角色不是「第二块屏」，而是**链接的中转站**——
教程、博客、分享卡的链接先落进手机微信 / QQ，再被带到 PC。这条路径上：
- 自定义 scheme（`brewlibrary://`）在手机上点了是**死链**；
- 华为 **App Linking**（https 链接 + 应用内路由）在 PC 上唤起 App，落在手机上至少是一个
  静态说明页（「BrewLibrary 是鸿蒙 PC 的 brew 客户端，这是 ffmpeg 的包页，请在鸿蒙 PC
  打开」+ 应用获取方式）。

**曾提出给 K 增加实施注记**：深链协议采用自定义 scheme + App Linking 双注册。

> **裁定（2026-11-22）：否决。** App Linking 需要额外做并维护一套网页落点，投入产出
> 不成立。K 维持纯自定义 scheme；「链接中转站」场景放弃救济。

## 3. 新增条目

### 3.1 U · 系统助手直达（意图框架）· 实验性 ❌ 已裁定否决

**一句话**：「小艺，装 ffmpeg」——通过意图框架把「安装 / 查询包」注册为系统可识别意图，
系统助手成为 brew 的一个入口。

- **推导**：触达类的极致形态。「命令行软件世界的应用商店」这个主旨，在入口层的对应物
  就是：AppGallery 靠桌面图标和系统搜索被找到，BrewLibrary 靠系统助手被找到。
- **眼前一亮**：没有任何包管理工具接过系统助手的指令；在鸿蒙上这是平台级差异化的入口。
- **实用价值**：把「想起→打开 App→搜索→安装」压缩成一句话；与 D2（自然语言找包）
  形成两层：应用内的 NL 找包 vs 系统级的意图直达。
- **实现路径**：⚠️ 待实测——Intents Kit 在 2in1 / PC 上的支持度、小艺在 PC 的意图触发
  形态（语音 / 文本 / 系统搜索框）均需真机验证后再定实施计划。
- **成本**：中（意图注册 + 路由承接，复用 K 的深链路由）。
- **风险**：PC 意图生态尚早期，触发率可能很低；按「实测先行」处理，验证通过前不排期。

> **裁定（2026-11-22）：否决。** Intents Kit 可以当作不存在；小艺 Agent 在 2in1 上不可用。
> 该条目关闭，相关平台事实修正移入 `round5.md` §2（AI 能力只能 BYOK）。

### 3.2 V · 系统入口二件套（文件关联 + 桌面快捷方式）❌ 已裁定否决

**一句话**：双击 `.brewfile` 文件直接进迁移导入页；桌面图标长按菜单直挂「升级中心」
「已装工具」两个快捷方式。

| 子项 | 内容 | 对 brew 的好处 | 成本 |
|---|---|---|---|
| V1 文件关联 | 应用注册 `VIEW` 动作 + `uris`，文件管理器双击 Brewfile → 直达 B 导入页（与 S1 拖拽并列的第二个原生入口） | 迁移场景从「打开 App → 找入口 → 选文件」缩到「双击文件」 | 低-中 ⚠️ 文件管理器「打开方式」对第三方扩展名的行为需实测；B 导出时顺带使用 `.brewfile` 扩展名自证关联 |
| V2 桌面快捷方式 | `shortcuts` 配置「升级中心 / 已装工具」，长按图标直达 | 更新哨兵（H）的第二入口：不通知时用户「想查一眼」的路径也变短；配合 H 形成完整触达闭环 | 低 |

- **眼前一亮 / 实用价值**：都是「只有装进系统的原生应用才配拥有」的入口——终端与
  网页应用做不到；单项不大，合起来把「brew 长在系统上」做实。

> **裁定（2026-11-22）：否决，完全没有意义。** 条目关闭。

### 3.3 W · 跨 PC 工具清单同步（账号云同步）· 可选 ✅ 裁定保留并收窄

**一句话**：两台鸿蒙 PC（桌面机 + 笔记本）登录同一华为账号，Brewfile 与已装清单经
账号数据云同步，「换台电脑，工具链还在」。

- **推导**：记忆类。与 round1 否决的「跨端到手机」不同——两端都是真开发机，场景成立。
- **实用价值**：真实但偏窄（多 PC 开发者）；**建议不单独立项**，作为 B（迁移工作台）的
  可选增强挂在导出链路上（导出的 Brewfile 顺手同步到账号云空间）。
- **风险**：云同步引入「数据离开设备」的隐私叙事变化，与零内置 / 本地优先的性格需要
  一句明确的用户协议（默认关、显式开启）。

> **裁定（2026-11-22）：保留但收窄。** 需求方顾虑：①会买两台鸿蒙 PC 的人太少；②同步
> Brewfile 可能太庞大。收窄为**只同步主动安装（install-on-request）的库**，动机锚定两个
> 场景：「换机时一键复制旧电脑 CLI 环境」「台式机 + 笔记本双机互见」。收窄版展开见
> `round5.md` §4（W′）。

### 3.4 增强注记（并入既有条目，不单独立项）

| 挂靠 | 注记 |
|---|---|
| H 更新哨兵 | 通知带**动作按钮**（「全部升级」/「稍后」），点按直达升级队列——通知类特性对 brew 的增益主要靠按钮完成闭环，不靠文案 |
| K 深链 | ❌ App Linking 注记已裁定否决（需要额外网页落点）；K 维持纯自定义 scheme |
| R 分享卡 | **二维码定位修正**：PC 用户「复制链接」是第一路径；二维码面向「投影 / 打印 / 群图」三个物理传播场景。不夸大扫码价值——扫码在 PC 上落回手机是死路（§2），卡片的分享按钮应以「存图 + 复制链接」为主 |

## 4. 鸿蒙特性判定总表（认真过滤的证据）

| 特性 | 判定 | 理由 |
|---|---|---|
| 通知 Notification | ✅ 已立项 | H 更新哨兵的载体；brew 事实触达的主通道 |
| 服务卡片 Form Kit | ✅ 已立项 | H 的桌面形态；官方支持 PC/2in1（round2 事实前提 #1） |
| 自定义 scheme 深链 | ✅ 已立项（K） | App Linking 需要额外网页落点，裁定否决（§2） |
| 系统分享 / 拖拽 | ✅ 已立项 | R / S1 |
| 多窗口 / 独立执行窗 | ✅ 已立项 | S2 |
| 华为账号 | ✅ 已在用 | 「我的」页账号能力 |
| 关键资产存储 Asset Store Kit | 🆕 X 的密钥安全存储 | 远程管理（round5 X）存 SSH 私钥口令的正道——通过 §1 判据的鸿蒙特性 |
| 意图框架 Intents Kit | ❌ 裁定否决（U） | Intents Kit 可当不存在；小艺 Agent 在 2in1 不可用 |
| 文件关联 + 快捷方式 | ❌ 裁定否决（V） | 需求方裁定完全没有意义 |
| 账号云同步 | 🆕 W′，收窄版（round5 §4） | 仅主动安装清单；换机一键复制 + 双机互见；默认关 |
| **一多移植浏览到手机** | ❌ 不做 | 需求方判断正确（§2），维持 round1 §3-4 否决；手机只做链接落点页 |
| 分布式流转 / 应用接续 | ❌ 不做 | brew 场景全是单机本地事实；无跨端任务可接续 |
| Push Kit 服务端推送 | ❌ 不做 | 违背零服务端性格；更新是设备本地事实，workScheduler 本地检查已覆盖 |
| 元服务 / 原子化服务 | ❌ 不做 | brew 的执行与文件权限要求完整应用形态；卡片化拆分无收益 |
| 实况窗 Live View | ❌ 不做 | 宿主形态与场景（外卖式时间线）不符；安装进度归 Q 的透视视图 |
| 超级中转站取命令 | ❌ 不做 | 应用内执行通道已闭环；pc_normal 也有复制路径，边际价值≈0 |
| 分布式数据对象 / 跨设备迁移 | ❌ 不做 | 同上「分布式流转」 |

> 这张表的用途：答辩 / 评审时直接展示「鸿蒙特性不是堆的，是筛的」——每一条不做都有
> 与主旨一致的理由，每一条做都指向 brew 体验的缩短路径。
