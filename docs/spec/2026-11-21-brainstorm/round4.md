## 1. 判据：鸿蒙特性对 brew 的真正角色

**核心事实**：brew 的使用模型是「不开 App」——用户在终端里干活，不会主动打开一个包管理
App。这意味着鸿蒙特性对 brew 的价值只有一条主线：

> **把 brew 的事实（可升级 / 上榜 / 装好了）和动作（安装 / 升级 / 导入）长到系统界面上，
> 让 brew 的服务不打开 App 也在发生。**

判据：任何特性必须缩短「brew 发生了一件事 / 用户想做一件事」到「完成」的路径。
按此判据，鸿蒙特性分成三类有用 + 一类不做：

| 类 | 特性做的事 | 对 brew 的意义 | 条目归属 |
|---|---|---|---|
| **触达** | 通知 / 服务卡片 | brew 的事实主动找到用户；用户不逛 App 也被服务 | H（已立项） |
| **入口** | 深链 / 分享卡 / 拖拽 | 用户想做一件事时，入口离得更近 | K / R / S1（已立项） |
| **空间** | 多窗口 / 独立执行窗 | 长任务不打断工作流 | S2（已立项） |
| **记忆** | 分布式数据同步（distributedKVStore） | 多台鸿蒙 PC 组网互见工具清单 | W′（`round5.md` §2，已立项） |
| 不做 | 一切「为了用特性而用」 | 见 `rejected.md` | — |

## 2. 增强注记（并入既有条目，不单独立项）

| 挂靠 | 注记 |
|---|---|
| H 更新哨兵 | 通知带**动作按钮**（「全部升级」/「稍后」），点按直达升级队列——通知类特性对 brew 的增益主要靠按钮完成闭环，不靠文案 |
| R 分享卡 | **二维码定位修正**：PC 用户「复制链接」是第一路径；二维码面向「投影 / 打印 / 群图」三个物理传播场景。不夸大扫码价值，卡片的分享按钮应以「存图 + 复制链接」为主 |
