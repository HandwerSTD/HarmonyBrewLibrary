# 头脑风暴 · 第 8 轮：Brew Lens——现有搜索的 AI 升级

> 日期：2026-11-23
>
> 本轮从“GUI 相比 brew CLI、HarmonyOS 相比普通桌面 GUI 的本质增量”出发。
> 记录一个新候选，并纠正上一版对 GUI 日志价值的判断。
>
> 状态：用户认可 Brew Lens 方向，并进一步明确它是现有搜索的 AI 升级，而不是另建独立搜索产品或平行导航入口；先做系统能力探针，再决定系统情境能力的优先级。

---

## 1. 对 GUI 主线的纠偏

上一版提出的“语义执行台”希望把日志里的包名、依赖、路径和错误变成可交互对象。这个方向不作为 GUI 主线，理由如下：

- GUI 的价值本来就是替用户消化命令和日志，减少用户对执行细节的关注；
- 正常安装时重新强调日志，会把已经被 GUI 隐藏的复杂度重新拉回界面；
- 用户通常只在报错后才需要查看细节，日志应当默认退居后台；
- 点击日志对象、展开结构化过程等能力，最多作为错误现场的按需诊断，不单独构成产品创新。

因此，现有 Q「安装实时进度 + 落盘 diff」仍应保持“结果和进度优先、原始日志按需查看”的原则。本文件不新增语义执行台候选。

## 2. 一句话

> **Brew Lens 是 BrewLibrary 现有搜索的 AI 升级：同一个搜索入口，不再只匹配包名，还能理解自然语言、安装命令、命令别名和用户从其他应用分享的文本，返回经过本地目录验证的真实软件包。**

当这套搜索能力延伸到浏览器、文档、聊天或终端的选中文本时，它表现为 HarmonyOS 的“软件包词典”。但它不是独立的第二套搜索，也不另占一个平行导航入口。

### 一个搜索，四种输入

| 输入方式 | 用户示例 | 搜索需要理解的内容 |
|---|---|---|
| 关键词 | `ffmpeg` | 传统名称、别名与全文匹配 |
| 自然语言 | `我想批量压缩视频` | 用户意图与任务语义 |
| 安装命令 | `sudo apt install ffmpeg ripgrep` | 跨生态包名、命令名与多项实体 |
| 系统分享文本 | 从浏览器或文档选中一段教程 | 当前情境中的软件实体与安装需求 |

四者共用同一套搜索结果、包详情、本机状态、AI Companion 和安装预演，不制造不同的结果体系。

正式路演话术：

> “普通应用市场只会匹配用户输入的包名；BrewLibrary 的 AI 搜索能理解用户想做什么、教程要求装什么，还能在用户看到软件的地方直接认出软件。”

## 3. 大众痛点

目标用户经常在应用市场之外接触软件：

- 在浏览器教程里看到 `apt install ffmpeg`；
- 在 README 里看到一串依赖和安装命令；
- 在聊天里收到别人推荐的命令行工具；
- 在终端或技术文章里看到 `rg`、`fd`、`bat` 等陌生名称；
- 看到软件名后，不知道 HarmonyOS 上是否有、自己是否已经装过、应该搜哪个包。

现有路径要求用户离开当前内容，打开 BrewLibrary，逐个复制、搜索、辨别包名，再决定是否安装。真正被打断的是正在进行的阅读、学习或开发任务。

Brew Lens 解决的是一类普遍问题：

> **“我正在看的这个东西，在 BrewLibrary 里到底是什么，我能不能用？”**

## 4. 核心闭环

### 4.1 系统情境输入

用户选中文字后，通过系统提供的选择菜单、分享能力或其他合规入口交给 Brew Lens。

输入可以是：

- 单个软件名：`ffmpeg`；
- 可执行命令名：`rg`；
- 单条安装命令：`brew install ffmpeg`；
- 跨生态命令：`sudo apt install ffmpeg ripgrep`；
- 混有解释文字的教程片段。

MVP 只处理用户明确选中的文字。不监听全局剪贴板，不读取无关应用内容，不把屏幕识屏作为成立前提。

### 4.2 本地识包与状态合并

识别管线依次完成：

1. 清理 Shell 提示符、命令前缀、选项和路径；
2. 识别包名、可执行命令名及候选别名；
3. 通过本地全量目录、BrewMapper 跨生态映射和候选名链匹配真实包；
4. 合并 upstream/Harmonybrew 双源状态；
5. 合并本机安装快照，区分未安装、已安装、可升级；
6. 给出每个候选的匹配依据和置信状态。

确定性规则优先。AI 只负责模糊语义、别名和复杂文本理解，候选必须经过本地目录过滤。无 Key 或断网时仍应完成常见命令和软件名的识别。

### 4.3 轻量结果卡

识别结果优先以轻量卡片、半页面板或系统支持的上下文界面呈现，不默认把用户拉进完整应用首页。

首屏只回答四个问题：

| 问题 | 卡片内容 |
|---|---|
| 它是什么 | 中文一句话简介与真实包名 |
| 我的设备有吗 | 双源可用性与无法验证状态 |
| 我装过吗 | 本机安装、版本与可升级状态 |
| 接下来能做什么 | 查看详情、问 AI、加入清单、安装预演 |

多项识别结果按教程中的原始顺序排列，并去重。不能可靠匹配的项目显示“未确认”，不以近似包名冒充确定答案。

### 4.4 连续动作

用户可从结果卡继续：

- 查看完整包详情；
- 带着原文和识别上下文询问 AI Companion；
- 收藏或加入主动安装清单；
- 合并多项结果进入既有 install dry-run；
- 在详情页完成最终安装确认。

Brew Lens 不执行用户粘贴或分享的原始命令，不允许 AI 生成命令直接运行。

## 5. 决赛 Demo

### 场景

用户在浏览器阅读一篇 Linux 开发教程，看到：

```bash
sudo apt install ffmpeg ripgrep
```

用户选中这段命令并调用 Brew Lens。

### 演示步骤

1. 当前页面旁出现 Brew Lens 轻量结果，而不是跳到应用市场首页；
2. `ffmpeg` 显示为 Harmonybrew 可用、未安装，并给出中文简介；
3. `ripgrep` 显示为已安装，同时提示其可执行命令是 `rg`；
4. 用户点击 `ffmpeg`，进入已有安装预演，查看将发生的变化；
5. 返回原教程后，可以继续在 Brew Lens 中问“它和 HandBrake 有什么区别”。

### 评委看到的核心差异

- 不是又一个搜索框，而是应用市场进入用户真实的软件发现现场；
- 不是只做文字识别，而是把识别结果与双源目录、本机状态、AI 和安装预演连接起来；
- 用户不需要先理解 Homebrew，也不需要离开当前任务重新组织搜索关键词。

## 6. 与既有功能的关系

| 既有功能 | Brew Lens 的关系 |
|---|---|
| D2 AI 问需求 | 合并为同一个 AI Search：自然语言描述模糊意图，安装命令提供明确实体，系统分享文本提供外部情境；共享 AI Companion、本地目录校验和结果页 |
| AB 安装指令翻译 | 成为 AI Search 的命令解析与跨生态映射能力，不另设平行翻译器；Brew Lens 是整套 AI Search 的系统级情境形态 |
| K 深链 | 深链只负责打开指定页面；Brew Lens 还负责实体识别、状态合并和后续决策 |
| S 拖拽/外部输入 | 拖拽只改变输入方式；Brew Lens 的核心是跨应用识别后立即返回可操作结果 |
| tldr 候选名链 | 提供 `rg` 等命令名到包名的确定性映射资产 |
| J install dry-run | 负责识别后的安全安装预演，Brew Lens 不重复实现事务计算 |
| 小艺 Work Skill | 面向 Agent 调用；Brew Lens 面向用户正在处理的系统文本情境 |

边界：如果只实现“分享一段文字 → 打开普通搜索页”，系统级 Brew Lens 不成立，应降级为 AI Search 的入口优化。AI Search 本身仍可由自然语言、命令理解和确定性降级支撑。

## 7. 为什么搜索升级可能足够大

Brew Lens 不是在现有搜索旁边再做一个功能，而是把搜索从“字符串匹配器”升级为三层统一的软件发现系统：

1. **理解层**：统一理解关键词、用户意图、安装命令、跨生态包名和别名；
2. **情境层**：让同一套搜索进入浏览器、文档、聊天和终端的文本情境；
3. **事务层**：把搜索结果接到本机状态、AI、清单和安装预演。

它覆盖的不是少数高级安装场景，而是所有“不知道准确包名”或“先在其他地方看到工具，再考虑是否安装”的用户。

其大功能价值取决于搜索范式和完整闭环的升级，不取决于分享入口本身。

## 8. HarmonyOS 能力探针与降级

### P0：成立性探针

真机验证以下能力，任何结论以实际平台接口和权限为准：

- 其他应用能否通过系统分享或选择菜单把明确选中的文字交给 BrewLibrary；
- 是否支持轻量结果面板、半页 UI 或不完全打断当前任务的展示方式；
- 返回原应用后能否保留识别上下文；
- pc_acl 与 pc_normal 是否有一致的入口能力；
- 入口声明、后台限制和隐私审核要求。

### 降级顺序

1. 系统支持轻量面板：展示完整 Brew Lens 结果卡；
2. 不支持轻量面板：打开独立半页或紧凑识别页，而非完整首页；
3. 不支持系统选择菜单：使用标准分享入口；
4. 只能手动粘贴到现有搜索：保留应用内 AI Search，不再把系统级 Brew Lens 作为创新点宣传。

全局悬浮层、任意应用覆盖、后台剪贴板监听和自动读取屏幕均不是 MVP 承诺。

## 9. 隐私与安全

- 默认只处理用户明确分享或选中的文本；
- 规则解析、目录匹配和本机状态查询优先全部在端侧完成；
- 只有用户主动调用 AI 时，才发送完成识别所需的最小文本；
- 不保存原始教程、聊天记录或终端内容作为长期历史；
- 对疑似 Token、密码、路径和用户信息先脱敏；
- 不执行原始命令，不静默安装，不用 AI 猜测替代本地目录事实；
- 无匹配时明确显示未确认，不制造不存在的软件包。

## 10. 分期建议

### 阶段 0：系统探针与应用内验证并行

真机完成选中/分享文本入口、轻量展示和返回上下文验证；同时在现有搜索中验证自然语言和安装命令的理解效果。系统探针只决定 Brew Lens 的外部情境能力，不阻塞应用内 AI Search。

### 阶段 1：统一现有搜索

保留现有关键词搜索，在同一入口加入自然语言和安装命令理解：

> 关键词/自然语言/安装命令 → 统一实体解析 → 本地目录与本机状态 → 同一搜索结果页 → 包详情/安装预演。

AI Companion、AB 和现有搜索共用解析结果与页面，不建立平行导航。

### 阶段 2：系统级 Brew Lens

系统探针通过后，把同一个 AI Search 接到分享文本：

> 系统分享文本 → 同一识包管线 → 轻量结果 → 同一包详情/安装预演。

支持混合教程文本、跨生态批量命令、别名消歧、AI 追问、加入清单和多项预演。

### 阶段 3：更自然的系统情境

仅在平台能力得到验证后，增加选择菜单、轻量上下文卡片等更短的入口。截图 OCR、全局识屏和自动剪贴板检测不进入默认范围。

## 11. 验收指标

- 常见软件名、安装命令和命令别名的识别准确率；
- 未确认候选的误报率，尤其是近似包名和 hallucinated package；
- 从选中文字到看到首个有效结果所需时间与操作步数；
- 无 Key、断网时的规则识别覆盖率；
- 本机已安装/未安装状态的一致性；
- 从识别结果进入详情或安装预演的完成率；
- 返回原应用后任务上下文是否仍然清晰；
- 用户是否无需查看日志或理解 Homebrew 命令即可完成整个流程。

---

## 12. 当前取舍

- **Brew Lens：定位为现有搜索的 AI 升级，值得进入 P0 验证。** 应用内先统一关键词、自然语言和安装命令搜索；系统探针通过后再延伸到外部文本情境。AI Companion、AB 和 Brew Lens 是同一套 AI Search 的能力与形态，不是三项独立主功能。
- **语义执行台：不作为主线。** 正常流程隐藏日志，报错时再提供按需解释。
- **界面同传、应用资源病历、3D 软件宇宙：不进入候选。** 分别存在平台权限、CLI 使用形态和实用价值问题。

AI Search 的应用内价值不依赖系统接口；系统级 Brew Lens 能否成为创新展示点，则取决于一个硬条件：

> **它是否真能让用户在其他应用的当前情境中，用同一套搜索完成“选中 → 识包 → 看懂 → 预演”，而不是只多了一次分享和跳转。**
