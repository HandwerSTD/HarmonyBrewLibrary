## 2. 创新点

### 2.1 F · 磁盘管家（brew cleanup / autoremove 的 GUI 化）

**一句话**：让包管理器长出「存储管理」的眼睛——你的 brew 目录占了多少、旧版本吃了多少、多少依赖是没人要的孤儿，一目了然，一键回收。

- **眼前一亮**：没有任何 brew GUI 做过「磁盘视角」。brew 用户几乎无人知道旧版本 keg 和孤儿依赖悄悄吃掉多少 GB——`brew cleanup` 在终端里是一条无人敢盲跑的黑盒命令，GUI 把它翻译成「每包一行、逐条勾选、合计可释放 X GB」的清单，黑盒变成可审计的存储面板。
- **实用价值**：磁盘空间是 PC 用户的第一痛点，而 CLI 工具恰是「看不见的占坑者」。`brew cleanup -n` 与 `brew autoremove -n` 的 dry-run 输出自带每条目的文件数与体积，直接喂给列表。
- **实现路径**：执行通道（`features/pcnative` / `BrewCli`）跑 `cleanup -n` / `autoremove -n` → 解析逐条目列表 → 勾选回拼完整命令（带精确路径或 `--token` 白名单）→ 复用现有执行 Sheet 落地；执行后重新 dry-run 验证清零。
- **成本**：低-中（解析 dry-run 文本 + 一个新页面；无新数据源、无新权限）。
- **风险**：dry-run 输出格式需以设备 brew 实测为准；清理动作不可逆，交互上默认只展示、执行前二次确认（与现有执行 Sheet 的退出码提示一致）。

### 2.2 G · 卸载安全网（反向依赖检查）

**一句话**：卸载任何包之前先回答「谁还依赖它」——`brew uses --installed` 驱动的卸载确认页，无依赖显示「可放心卸载」，有依赖列出会被牵连的包。

- **眼前一亮**：应用商店卸载一个 App 从不告诉你会牵连谁（因为 App 之间无依赖）；而包管理器恰恰处处是依赖，却同样没人做这道检查。把「反向依赖查询」做成卸载的默认动作，是包 GUI 相对应用商店的结构性优势——只有包管理器能做，却没包管理器做了。
- **实用价值**：`ffmpeg` 这类被依赖大户，卸载后连带一圈工具失效，且失败发生在几天后的某条命令里，用户根本联想不到原因。卸载前的一道闸，成本一条命令。
- **实现路径**：本机包行 / 详情页的卸载入口 → `brew uses --installed <token>` → 结果渲染进确认 Sheet（零依赖 / N 个依赖方）；依赖方条目可点击跳转。
- **成本**：低（一条命令 + 确认页增量；执行通道现成）。
- **风险**：`uses` 仅覆盖 formula 关系；运行时软依赖（脚本里 `curl xxx`）查不到，文案需如实标注覆盖范围，不夸大「安全」。

### 2.3 H · 更新哨兵（outdated 通知 + PC 桌面卡片）

**一句话**：brew 永远不会主动说话——本应用替它说：定时刷新 outdated 集合，有新版本时经系统通知与桌面卡片提示「gh 有 2.63.0 可升级」，点开直达升级队列。

- **眼前一亮**：brew 的世界观里「更新靠用户想起来」，官方连 GUI 都不通知。把包管理补上「应用商店级」的更新触达（通知中心 + 服务卡片），是没人做过的常识性补全；而「CLI 工具有桌面卡片」这件事本身就是话题点。
- **实用价值**：CLI 工具的安全补丁与功能更新全靠撞运气；等待升级的包越积越多。通知 + 卡片把「想起来去查」变成「被告知」，且升级动作仍由用户确认（绝不静默升级，保持「不把用户当傻子」的性格）。
- **实现路径**：定时后台刷新（work scheduler / 长时任务，保活边界 ⚠️ 待实测）复用 `BrewInstalledLoader` 的 outdated 链路 → 变化时发通知（Notification Kit）→ Form Kit 卡片（官方支持 PC/2in1，事实前提 #1）展示待升级数，点击服务直达升级列表。
- **成本**：中（后台调度 + 通知 + 卡片三件套；数据链路零新增）。
- **风险**：⚠️ PC 上后台任务与卡片定时刷新的真实触发边界需真机实测后再定实施计划（沿用「实测先行」规矩）；通知频控需要用户可配置（关 / 每日 / 每周）。

### 2.4 I · tldr 用法示例集成（详情页从「是什么」到「怎么用」）

**一句话**：详情页在 caveats 之后补一块「怎么用」：按 token 懒加载 tldr 示例页，**中文页现成**，每条示例可一键复制或直接送进执行 Sheet 跑。

- **眼前一亮**：所有包详情（包括官方 BrewUI）都停在「这是什么」；没人想到把「人写的、经社区审校的真实用法示例」接进包详情。装完 wget 的下一秒就能抄到 `wget -c URL`，详情页第一次完整覆盖「找 → 装 → 用」。
- **实用价值**：`man` 是给记得命令名的人查参数的，新手要的是「抄了就能跑的三五行」。tldr 社区已提供中文翻译（`pages.zh`），连翻译成本都为零。
- **实现路径**：tldr 内容 CC BY 4.0（事实前提 #2），署名后可分发。按 token 懒加载 GitHub raw / 镜像的 `pages.zh/<token>.md`（失败回落 `pages/common/<token>.md`），渲染为示例卡（命令 + 注释行区分），每条带「复制」与「在终端执行」；落盘缓存沿用 `brew_live_data` 的 TTL 模式，离线可复用。**数据是「示例」而非「事实」**：无该 token 页面时静默隐藏区块，不造数据。
- **成本**：低-中（一个渲染组件 + 拉取缓存；无 AI 依赖、无幻觉风险）。
- **风险**：tldr 覆盖的是常用命令，长尾 formula 无页面（隐藏即可）；镜像可达性需实测（可选上游 raw / jsDelivr 双通道，与现有双数据源思想一致）。

### 2.5 J · 装机预演（dry-run 透视）

**一句话**：点「安装」之前先看「装下去会发生什么」：`brew install --dry-run` 摊开将安装的包清单、依赖树、体积与 caveats 预告，确认后才真跑。

- **眼前一亮**：应用商店下载前至少给个体积数字，brew GUI 没有任何一个做到安装前预览依赖与体积；而设备 brew 实测支持 `--dry-run`（`docs/knowledge/2026-11-21-brew-tap-trust.md`），能力早已躺在命令行里，只是没人把它翻译成 UI。
- **实用价值**：与 A（适配引擎）互补——A 回答「能不能装」，J 回答「装下去的代价」：额外拉进几个依赖、占多少盘、装完会不会在终端打印一堆要求手动做的事（caveats 提前看）。对「我只要一个 ffmpeg」的用户，这一屏就是决策依据。
- **实现路径**：详情页安装按钮 → 先跑 dry-run 解析 `Would install` 清单 → 预演 Sheet（清单 + 体积 + caveats 摘要）→「确认执行」升级为真实安装；与 A 的依赖缺口求解共用 per-token 详情拉取与缓存。
- **成本**：低-中；**建议并入 A 的交互设计**而非独立立项（A 的「查可装性」结果页天然就是 J 的载体）。
- **风险**：dry-run 在信任 tap 场景的行为已在实测笔记验证；caveats 体积大时摘要化呈现。

### 2.6 K · 深链安装协议（round1 §6.3 遗留项的正式表态：支持立项）

**一句话**：`brewlibrary://install/<token>`——社区教程、博客、README 里的一条链接，点开直达应用详情页并预填好安装命令，「从教程到装好」从三步变一步。

- **表态理由**：Harmonybrew 生态早期最稀缺的是**内容**（教程 / 评测 / 迁移指南），深链把内容作者变成分发渠道：作者贴一条链接，读者一键到达。这是生态冷启动期的杠杆，越早立协议越占位。
- **设计边界**：v1 只做「唤起详情页 + 预填命令」，**不做静默安装**——用户始终要看一眼详情（deprecated / 适配态）再确认，与本项目「不把用户当傻子」的价值观一致；协议同时支持 `detail` / `search` 两个只读动作，让教程可以链接搜索结果与详情页。
- **成本**：低（scheme 注册 + 路由参数解析，routerMap 现成）。
- **风险**：低；需在文档里冻结协议格式（v1），防止教程作者写了链接后续改版失效。

### 2.7 L · 版本时光机（升级翻车一键回滚）· 实验性

**一句话**：新版本把你的脚本搞坏了？回滚到上一个还能用的版本。

- **眼前一亮 / 实用价值**：应用商店从不需要回滚（App 版本不可选），包管理器恰恰年年遇到「升级即破坏」（上游 breaking change），而回滚在终端里是资深玩家才知道的暗黑操作。GUI 把它变成一个按钮。
- **实现路径（⚠️ 全部待实测）**：brew 的 bottle 下载缓存里若还有旧版 bottle，重装旧 bottle 即回滚；缓存已清则可评估 `brew extract`（生成历史版本本地 formula，慢但通用）。入口放在详情页版本区与本机包「待更新」行（升级前记录当前版本号是前置动作）。
- **成本**：中；**风险最高的一条**——依赖缓存状态与 Harmonybrew bottle 版本策略，先实测「升级 wget 后旧 bottle 是否仍在缓存」再决定立项。

### 2.8 M · 内网 bottle 搬运（离线开发机分发）· 实验性

**一句话**：有网的机器上 `brew install --cache` 只下不装，bottle 文件经中转站 / 文件管理拷给内网开发机，放进 brew 缓存目录后离线安装。

- **眼前一亮**：「从一台 PC 把命令行软件搬给另一台」没有任何现有工具做；而这正是企业内网开发机的真实日常（ Harmonybrew 本来就是为国内网络环境而生的镜像，离线场景是它的自然延伸）。
- **实用价值**：对内网开发者是刚需级便利；对本项目是「Harmonybrew 生态唯一分发通道」（`docs/knowledge/2026-11-21-brew-tap-trust.md`：HiShell 强制签名）这一平台事实的 GUI 化收割。
- **实现路径（⚠️ 待实测）**：A 机跑 `brew install --cache <token>` → 定位缓存产物（哈希校验信息 brew 自带）→ 用户经系统分享 / 文件管理拷贝 → B 机应用把文件放入对应缓存路径 → `brew install` 离线命中缓存。可行性核心在 B 机 brew 对缓存命中与 SHA 校验的行为实测。
- **成本**：中-高；用户面窄（内网场景），作为 wild card 保留，不进第一梯队。

## 4. 遗留与下一步

1. 三件实测先行的验证动作可立即做，结论直接决定 L / H / M 是否立项：
   - 设备 `brew cleanup -n` / `autoremove -n` 输出格式采样（F 的解析口径）；
   - 升级一个包后旧 bottle 是否仍在缓存（L）；
   - PC 真机上 work scheduler 触发与 Form Kit 卡片刷新行为（H）。
2. K 的协议格式建议在 `docs/` 立一份 v1 冻结文档（scheme、参数、动作枚举）。
3. 否决项统一见 `rejected.md`；本轮未触碰任何否决方向。
4. 后续轮次写入本目录 `round3.md`。
