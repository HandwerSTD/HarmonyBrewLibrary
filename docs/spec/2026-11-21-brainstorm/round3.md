## 1. 特点清单（推导的原料）

下表是 BrewLibrary **独有的、别的 brew 客户端（含官方 BrewUI）没有的**东西。每一条都是能力资产，不是功能。

| # | 独有特点 | 载体 | 别人为什么没有 |
|---|---|---|---|
| T1 | **结构化的包详情页**（11 分区：desc / 版本 / 依赖 / bottle 标签 / artifacts / caveats / 生命周期 / 热度） | `features/brewdetail` | 终端 `brew info` 是纯文本；BrewUI 也没有分区块 |
| T2 | **GUI 图形化能力**——全部数据已经在端上结构化，只差「画出来」 | ArkUI 全程 | 终端的一切都是文本；GUI 的本质优势就是可视化 |
| T3 | **端侧零依赖搜索引擎**（16k token + desc 全量索引，纯函数） | `BrewSearchEngine` | 官方检索必联网；BrewUI 无本地索引 |
| T4 | **自建分类体系**（16 分类，设备端现算）+ **六张榜单设备端现算、口径可解释** | `BrewTaxonomy` / `BrewCatalogAlgo` | 上游 API 没有分类字段；榜单算法口径从未被做成过 UI |
| T5 | **双目录在端侧**（上游全量索引 × Harmonybrew catalog）+ **stats 日下载量 90 天逐日缓存** | fullsync / `HarmonybrewStats` | 适配断层只有这个平台有；日粒度数据已逐日落盘但没人逐日读它 |
| T6 | **直连 brew 的本机执行通道**（NAPI + Shell，流式输出探针 `ShellStreamProbe`，执行 Sheet ANSI 配色） | `features/pcnative` | 唯一在沙箱内打通 brew 命令链路的鸿蒙应用 |
| T7 | **PC 桌面形态**（大屏、多窗口、拖拽、键盘、服务卡片官方支持 PC/2in1、系统分享） | `features/pcui` | 终端不占桌面；BrewUI 在 macOS 有但鸿蒙无人做 |
| T8 | **透明性格**（零内置快照、口径落盘可审计、失败六分类不吞错） | 全局设计原则 | 这是项目性格，可以直接变成交互 |

**本轮可视化的有用性判据**（回应「图形化怎么才有用」）：
可视化的价值 = **把原本要读很多行文本 / 跑很多条命令才能得出的结论，压缩成一眼可得的判断**。
画图不是为了好看——每个图必须回答一个「文本回答不了或很费劲」的问题；答案一眼可得的图，就是有用。
下面每个可视化条目都显式写出它回答的问题。

## 2. 创新点

### 2.1 N · 生态晴雨表（适配地图 × 活性大盘）

**一句话**：一页看懂「鸿蒙 brew 生态」——16 个分类各被 Harmonybrew 覆盖了多少（适配地图），全生态每天下载多少、哪天爆了什么（活性大盘）。

- **推导链**：T2（可视化）× T5（双目录 + 日粒度 stats 已在盘上）。
- **回答的问题**：①「这个平台的包生态到底能不能用、缺在哪？」——适配地图：每个分类一根条，「开发工具已适配上游 92%，媒体工具仅 45%」一眼可比；②「这生态是活的还是死的？」——活性大盘：90 天全生态日下载曲线，峰值日点开就是「那天爆红的包」（per-day token 增量 diff，数据已在盘）。
- **眼前一亮**：「适配断层」在 related work 调研（`relatedwork.md`）里是三个段落的话，变成一张图就是一个论点；全生态下载大盘没有任何工具画过——Harmonybrew 自己都没展示。
- **实用价值**：观望者用它判断「值不值得迁」（related work 调研定位的「晴雨表」角色第一次有了实体页）；生态建设者用它看 backlog 分布；普通用户点分类直达「只看鸿蒙可装」列表（衔接 A）。
- **实现路径**：全端侧。适配地图 = 两目录 token 集合 join 后按 `BrewTaxonomy` 分类聚合（A 的数据副产物）；大盘 = `HarmonybrewStats` 已缓存的日文件求和 + 逐日 top 增量（round1 §1.2 注明「当前只被 sum 成窗口，没人逐日读它」——本条正好把这笔闲置资产用起来）。所有数字带数据日期戳（T8）。
- **成本**：低-中。**与 A 同期做收益最大**（join 结果一鱼两吃）。

### 2.2 O · 依赖图谱（正向树 × 卸载影响图）

**一句话**：依赖不再是一行行 token 文本：详情页画正向依赖树，卸载确认画「会影响谁」的反向图。

- **推导链**：T1（详情页已有依赖字段）× T2（可视化）× T6（`brew uses --installed`）。
- **回答的问题**：①「装 ffmpeg 会拖进来多少东西？」——正向树（dry-run 预演 J 的可视化载体）；②「卸掉它，谁会坏？」——反向影响图（G 的确认页从文字列表升级为关系图）。
- **眼前一亮**：终端里依赖是缩进文本，BrewUI 只有平铺列表；把「依赖」画成图这件事在包管理 GUI 里几乎无人做透——而它恰恰是 GUI 相对终端的**本质优势**，不做白不做。
- **实用价值**：依赖深度决定安装体积与卸载风险，是「我只要一个 ffmpeg」用户最缺的判断依据；反向图让 G 的安全网从「提示」变「证据」。
- **实现路径**：懒加载 per-token 详情拿 `dependsOn` 闭包（与 A/J 共用缓存）；闭环检测防循环依赖；节点点击跳详情。反向图复用 G 的命令输出。
- **成本**：中（图布局组件是主要工作量；数据全现成）。

### 2.3 P · 榜单溯源卡 → 已否决移除（2026-11-22）

原提案（每张榜条目的「为什么」入口，点开看 vel / vol / 口径窗口与在榜数字，把可解释性从文档变成交互）已于 2026-11-22 被需求方裁定否决——理由与完整记录见 `rejected.md` §1 第 16 条。口径透明保留在算法文档（`docs/brew-discover-algo.md`）与产品性格中，不作为展示功能。

### 2.4 Q · 安装透视（实时进度 × 落盘 diff）· 实验性

**一句话**：安装从「滚动文本」变成「进度视图」：实时解析流式输出画进度条，装完展示「写进了哪些目录、新增多少文件」。

- **推导链**：T6（执行通道 + `ShellStreamProbe` 流式探针已在）× T2。
- **回答的问题**：「装这个大包是卡住了还是在动？」——brew 在终端里刷屏，在 GUI 里如果只显示转圈就比终端退步了；透视让它比终端**信息更多**。
- **眼前一亮**：把「一个命令的输出」升级为「一次安装的过程视图」——进度、阶段（Downloading→Pouring→Linking）、完成后 Cellar 前后 diff。没人做过，因为它同时需要流式探针（已有）和文件系统能力。
- **实现路径**：⚠️ 实测先行——流式输出的阶段解析（探针已在，吞吐量验证）；落盘 diff 用安装前后对 Cellar/Caskroom 目录快照对比（`pc_acl` 有用户文件读权限，路径实测确认）。
- **成本**：中；风险集中在流式吞吐与目录读取，先做输出解析半段（进度条）已经成立，落盘 diff 可二期。

### 2.5 R · 包分享卡（深链 × 二维码 × 系统分享）

**一句话**：详情页一键生成分享卡：包名 + 一句话描述 + 适配徽章 + **二维码（内容即深链 `brewlibrary://install/<token>`）**，存图发群、贴进博客 README。

- **推导链**：T1（结构化内容就是卡的素材）× T7（系统分享）× K（深链协议）。
- **回答的问题**：「怎么把一个包推荐给别人？」——终端世界的方式是让对面复制一条命令；卡片把它变成一张可扫、可存、可发的图。
- **眼前一亮**：「分享包」这个动作在包管理器里从来不存在——分享卡让 K（深链）从协议变成**有传播载体**的协议：教程作者在文末贴二维码，读者扫码直达详情页。
- **实现路径**：卡片用 ArkUI 组件渲染 + 截图导出（componentSnapshot，⚠️ PC 真机验证）；二维码现成 API；适配徽章复用 A。
- **成本**：低-中。**与 K 捆绑立项**——K 是协议，R 是协议的翅膀。

### 2.6 S · PC 原生交互三件套（大屏形态的红利）

**一句话**：把「这是台电脑」用足：拖拽导入 Brewfile、执行 Sheet 升级为独立窗口/可分屏、全局命令面板（Ctrl+K）。

| 子项 | 推导链 | 回答的问题 / 价值 | 成本 |
|---|---|---|---|
| S1 拖拽导入 Brewfile | T7 拖拽 × B′ 工作台 | 「怎么把 Brewfile 弄进来？」——从文件管理拖进窗口即开始解析，B′ 的**PC 原生入口**，比粘贴高一档 | 低-中 ⚠️ 拖拽事件真机验证 |
| S2 执行 Sheet 独立窗口 | T7 多窗口 × T6 执行通道 | 「一边装一边继续逛」——长任务不再被 Sheet 挡住全屏，PC 多窗口是天然解法 | 中 |
| S3 全局命令面板 | T7 键盘 × T3 搜索引擎 | 「老手不想点五层导航」——Ctrl+K 唤起，复用端侧索引：搜包、跳页、执行历史命令 | 低-中 |

- **眼前一亮 / 实用价值**：三项都是「终端与网页都给不了、只有原生桌面能给」的交互；S1 之于 B′、S3 之于 T3 都是既有资产的免费放大器。

### 2.7 F+ · 磁盘管家升维：占用 Treemap

**一句话**：round2 F 的列表视图之上加一层 Treemap——brew 目录占用地图像 DaisyDisk 一样一块块摆开，谁最占地一眼定位。

- **推导链**：T2 × F（`cleanup -n` 已解析出每条目体积）。
- **回答的问题**：「50 GB 里谁是大头？」——排序列表要读 N 行，Treemap 一眼；对「磁盘管家」的目标用户（被空间焦虑驱动的人），这一眼就是产品价值本身。
- **实现路径**：数据零新增（F 的解析结果直接聚合）；自绘 Treemap（ArkUI Canvas，榜单渐变卡头已有自绘先例）。
- **成本**：中（纯视觉层，挂在 F 上做）。
