# 头脑风暴 Round 6 · 应用市场主线内的三个大功能

> 日期：2026-11-23。状态：三个候选均保留，尚未立项；不改变 `decisions.md` 的既有优先级。
> 编号说明：X 已用于 round5 的远程控制台否决项；本轮新增 Y、Z、AA。
> 本轮选题纠偏：BrewLibrary 的核心定位仍是 **Homebrew GUI 应用市场**。创新应继续深耕
> 「发现—了解—比较—安装—更新—管理—卸载」，不扩张为项目环境管理平台、通用任务自动化
> 平台或终端工作流工具。

## 1. Y · 更新情报中心（Release Intelligence）

**一句话**：不只告诉用户「有更新」，还告诉用户「发生了什么、与当前版本差在哪里、是否值得
现在更新」，把更新列表从版本号提示升级为更新决策中心。

### 1.1 真实痛点

用户看到 `ffmpeg 7 → 8`、`node 22 → 24`，通常不知道更新了什么、有没有不兼容变更、是否
值得马上更新，以及更新后会增加哪些依赖、占用多少空间。传统包管理器只提供一个待更新数字，
用户只能盲目更新，或者一直不更新。

### 1.2 功能闭环

- 自动关联上游 Release Notes、更新日志与 formula 变更；
- 生成中文更新摘要，区分新功能、修复与重大变更；
- 对比更新前后的依赖数量、安装体积、命令变化、软件源与版本变化；
- 识别「大版本升级」「配置不兼容」「安全修复」等关键事件；
- 支持单包忽略本次版本、暂停提醒、固定版本等更新策略；
- 更新完成后保留本次更新档案，供日后追溯。

### 1.3 决赛 Demo

展示一批可更新包，其中普通更新可以直接处理；点开一个大版本更新，页面明确提示：

> 本次升级包含 3 项不兼容变更，新增 2 个依赖，预计增加 38 MB；以下是与你当前使用方式
> 相关的一项变化。

用户看完情报后，再决定更新还是暂缓。

### 1.4 为什么是大功能

它需要版本数据采集、上游发行日志关联、公式历史差异、中文摘要、风险识别和单包更新策略，
是一套完整的数据系统，而不是给更新列表加几行文字。

### 1.5 与既有条目的关系及边界

- 与 H 更新哨兵：**H 负责发现更新，Y 负责理解更新**；通知与卡片仍只负责触达和跳转。
- 与 L 版本时光机：Y 服务更新前决策，L 服务更新后的实验性恢复，两者不能互相替代。
- 不做静默升级；「未发现重大变更」不等于「保证升级安全」。
- 上游没有可靠 Release Notes 时必须显示信息缺口，不能由 AI 编造更新内容。

## 2. Z · Brew Compare 应用对比与替代中心

**一句话**：从「找到几个名字相似的包」升级为「看懂它们的差异、知道哪个适合自己、能否替代
现有工具」。

### 2.1 真实痛点

`grep` / `ripgrep`、`cat` / `bat`、`find` / `fd` 等工具解决相似问题。用户能找到包，却很难
判断它们到底有什么区别、应该装哪个，以及能否替代现在正在使用的工具。

### 2.2 功能闭环

每个包除详情外，还拥有一组结构化关系：

- **同类工具**；
- **可替代工具**；
- **互补工具**；
- **经常一起使用**。

进入对比模式后，按类别使用不同的比较维度：适用场景、核心能力差异、命令及使用方式、依赖和
安装体积、许可证、维护活跃度、HarmonyOS 软件源适配状态、真实安装统计，以及从旧工具迁移时
需要注意的差异。候选可以直接加入安装计划，让比较闭环到市场的主行为。

### 2.3 决赛 Demo

从 `grep` 详情页进入「寻找替代工具」，选择 `ripgrep` 对比。系统不是简单并排两个详情页，
而是直接回答：

> 两者都能搜索文本；如果主要搜索大型代码目录，可以重点考虑后者；如果依赖某些传统选项，
> 需要确认这些迁移差异。

用户可以直接把候选加入安装计划。

### 2.4 为什么是大功能

真正的难点是建立**软件替代关系图谱和分类比较模型**，而不是画一个对比表格。它会同时增强
搜索、详情、榜单、AI 推荐和安装转化，是应用市场的基础设施。

### 2.5 与既有条目的关系及边界

- 与 D2 自然语言找包：AI Companion 负责开放式问答；Z 负责有证据、可复核的结构化选型。
- 与 O 依赖图谱：O 表达 brew 的依赖关系；Z 表达面向用户选型的同类、替代与互补关系。
- 比较依据必须来自结构化数据和真实元数据，AI 只负责解释事实，不能自由编造参数或结论。
- 「可替代」必须限定场景，不能宣称两个工具在所有用途上完全等价。

## 3. AA · Brew Preview 终端应用试看

**一句话**：给 CLI 应用补上应用商店式的「截图与视频」——安装前即可试看真实命令、真实输入
和真实输出。

### 3.1 真实痛点

GUI 应用商店有截图和视频，用户一眼就知道软件能做什么；CLI 包通常只有一句抽象描述。即使
用户看到了简介，仍难以想象安装之后怎样使用、输出是什么样。

### 3.2 功能闭环

为重点软件包提供版本化、可播放的真实终端演示：

- 在详情页像应用商店截图一样直接试看；
- 展示真实命令、真实输入和真实输出；
- 按场景拆分，例如 ripgrep 的搜索项目、过滤文件、显示上下文，ffmpeg 的查看媒体信息、
  转换格式、压缩视频；
- 与 I tldr 示例联动，看完可以复制对应命令；
- 标明演示对应的包版本和验证环境；
- 新版本出现后重新验证演示，避免命令已经失效。

这里不需要在用户机器上执行，也不是把 BrewLibrary 变成任务工具；它仍然是在帮助用户
**安装前了解软件**。

### 3.3 决赛 Demo

打开一个陌生 CLI 工具，先展示传统元数据，再点击「试看」：20 秒内真实终端演示自动播放，
用户直接看到这个工具解决什么问题、如何使用、结果长什么样。

「CLI 应用也能拥有应用商店式预览」是无需技术背景也能理解的展示点。

### 3.4 为什么是大功能

如果只是人工上传几个视频，那确实是小功能；只有建立**演示格式、批量制作流程、版本绑定和
自动复验机制**，让内容能够持续覆盖大量包，它才是大功能。

### 3.5 与既有条目的关系及边界

- 与 I tldr：tldr 是静态、可复制的用法示例；AA 是带真实输入输出的版本化试看，两者联动而非
  互相替代。
- 与 D1 AI 讲解包：AI 负责解释，AA 提供可观看、可复验的事实材料。
- 优先覆盖热门和重点包，不一开始承诺全量 16,356 包。
- 演示必须标注来源和验证版本，不能把剪辑效果冒充真实运行结果。

## 4. 优先级与组合叙事

| 条目 | 用户价值 | 决赛表现 | 主要成本 | 本轮建议 |
|---|---|---|---|---|
| Y · 更新情报中心 | 极高，覆盖所有已装机用户 | 强 | 版本数据与日志关联 | 三个候选中优先深化 |
| Z · Brew Compare | 高，解决选型困难 | 强 | 替代关系图谱与结构化数据 | 第二主功能候选 |
| AA · Brew Preview | 高，尤其帮助新用户 | 最直观 | 内容制作与持续复验 | 展示型候选，先做重点包 |

三者与既有能力可以组成一条不偏离 Homebrew GUI 应用市场的叙事：

> **AI Companion 让用户找得到，Brew Compare 让用户选得准，安装预演让用户装得放心，
> 更新情报中心让用户更新得明白。**
