# 目录全量同步与浏览集放开（spec + plan）

> 状态：**待评审**（决策点见 §6）
>
> **前提假设（贯穿全文）**：目标形态只有 `pc`（2in1 = PC），**假定始终 WLAN** →
> ① 流量不作为约束（不做仅 Wi-Fi 判断、不做延迟启动、不做字节预算权衡、不做退避与开关）；
> ② **性能仍是硬约束，一律不简化**（首屏时间、内存峰值、扫描耗时、滚动帧率、落盘体积）。
>
> 目标一句话：**让浏览页的分类与列表随现网自动同步（新增包无需发版即可出现且分类正确），并去掉「前 100 个包」这个硬裁切。**

---

## 1. 现状（代码事实 + 本轮实测）

### 1.1 现有链路

```
① 目录（每小时最多 2 次 HEAD 探针）
   analytics 4 端点（30d/365d × formula/cask）
     → BrewCatalogAlgo.build()  现算三张榜 + 按 30d 安装量排序
     → BrewCatalog { boards(每榜 40), topTokens(每 kind 前 200) }  → Preference
② 浏览页构页（每次进页面）
   browseRows() = topTokens.slice(0, BREW_BROWSE_LIMIT = 100)      ← 硬裁切，本 spec 要改的就是它
     → 为这 100 个 token 逐个拉 /api/<kind>/<token>.json（并发 6，预算 15s）
     → 分类只能看 desc：BrewTaxonomy.categoryOf(kind, token, desc)
     → 没拿到 desc 的条目**不上屏**（宁缺不错，docs §5.3）
     → BrewBrowseBuilder 分组 → 分类卡（卡内预览 5 条 + 查看全部）
③ 详情页：单条 /api/<kind>/<token>.json（与 ② 共用同一份 TTL 缓存）
```

### 1.2 为什么会有这个 100

不是"显示上限"，而是**"能分类的包数上限"**：

- 官方 API **没有任何分类字段**，分类是自建词表（`lexicon.json` → `BrewTaxonomy`）的产物，
  判别顺序 = 策展覆盖 → 关键词（**看 desc**）→ 兜底。
- 于是 `desc` 是**构页输入**：拿不到 desc 就不能上屏（否则分类是错的）。
- `desc` 过去只能逐条拉（`/api/formula/<token>.json`），所以 100 是"一次进页面愿意花多少请求/时间"的预算。

### 1.3 本轮实测（`curl -sSI -H 'Accept-Encoding: gzip'`）

| 端点 | gzip 体积 | 内容 |
|---|---|---|
| `/api/formula.json` | **5,288,420 B ≈ 5.29 MB** | 全量 **8,611** formula，**每条都带 `desc`**（解压后 **32,368,020 B ≈ 30.9 MiB**） |
| `/api/cask.json` | **2,045,750 B ≈ 2.05 MB** | 全量 **7,745** cask；其中 **2,645 条 `desc` 是 `null`**（上游就没有描述），解压后 **18,884,870 B ≈ 18.0 MiB** |
| analytics 4 端点（现用） | 80,085 + 126,426 + 59,778 + 95,932 = **362 KB** | 只有 token + 安装量，**没有 desc** |
| 单条 `/api/formula/awscli.json` | **1,702 B ≈ 1.7 KB** | 现状就是靠它逐条拉 |

> 上面两个全量包的计数是**用真解析对账过的**（`len(json.load(...))` = 8,611 / 7,745，与扫描器的 `pairs` 一致）。
> 早先草稿里的「13,779」是估算失误，已废弃；真实对象总数是 **8,611 + 7,745 = 16,356**。

**推论（本 spec 的地基）**：把全量 16,356 个包的 `desc` 拉齐 ——

| 走法 | 字节 | 请求数 | 后台耗时量级 |
|---|---|---|---|
| 现状口径（逐条） | ≈ **28 MB**（16,356 × 1.7 KB） | **16,356 次** | 并发 6 下 ≈ 分钟级（真正的问题在这里，不在流量） |
| 全量元数据包 | **7.33 MB**（gzip 实测） | **2 次** | **21.7s**（真机实测，§4.6） |

全量包在两个维度上都更省；且**流量免费不等于请求数免费** —— 上万次请求带来的是分钟级的 CPU/网络 churn
（笔记本风扇、耗电、公共源的礼貌性），这才是要避开的东西。

文档 `§7.3` 那句「`/api/formula.json` 32.4 MB ❌ 严禁下发」的语境是**"在页面加载路径上下发"**，
本 spec 把它改成**后台的、不阻塞页面的**同步，语境变了，结论要重写（§10 有修订动作）。

## 2. 目标 / 非目标

### 2.1 目标

| # | 目标 | 可验证形式 |
|---|---|---|
| G1 | **列表随现网自动同步**：现网新增/下线包无需发版即反映到浏览页与分类 | 用现网真实新增（或改名）的 token 走查，不发版即可看到 |
| G2 | **去掉硬裁切**：浏览集不再被"能否拿到 desc"卡住 | `BREW_BROWSE_LIMIT` 删除；13k 全量参与分类与排序 |
| G3 | **首屏不劣化**（硬约束） | 冷启动首屏 p95 ≤ 现状（现状：~5s 出 100 条）；同步不在首屏 await 链上 |
| G4 | **性能不劣化**（硬约束） | 扫描耗时/峰值内存/滚动帧率/落盘体积全部有门槛，见 §7 |
| G5 | 分类正确性不下降（宁可少显示也不错分类） | 上屏条目兜底率 ≤ 现状基线 |

### 2.2 非目标（明确不做）

- **不做流量控制**：无仅 Wi-Fi 判断、无延迟启动、无新鲜窗口/退避常量、无用户开关（前提假设已放开）。
- **不做分页 / 加载更多**：PC 上直接全量列表 + 虚拟滚动（`LazyForEach` 只构建可见项），
  既没有"每页 N"，也不需要 `hasNextPage` 语义 —— 比"分页"更简单且性能达标。
- **词表自动同步**：`lexicon.json` / `BrewTaxonomy.ets` 仍随版本走 → 新包靠规则分类，判不出来的仍落兜底。
  （要把词表也做成可下载，需要托管地址，另立 spec。）
- 自建/托管服务端（本方案只用现网公共端点）。
- 搜索索引（`§11` 的搜索待办，依赖本 spec 产出的 `token → desc` 表，但另做）。
- 详情页数据链路不变（仍单条拉整份 doc）。

|---|---|---|---|---|---|
| **A. 全量元数据后台同步**（**已落地，见 §9 进度**） | 启动后后台拉 `formula.json` + `cask.json`，**一次拿完 32MB**，流式扫描抽 `token → desc` 落盘；分类改读本地表，硬裁切随之失效 | 7.34 MB / **2 次** | ✅ | 32 MB 文本的扫描成本 | **已实现** |

## 4. 选定方案 A 的设计

### 4.1 数据模型与存储

```ts
/** 现网元数据索引：只保分类与副标题需要的最小字段 */
interface BrewMetaIndex {
  ts: number;                              // 本次同步时间（仅用于日志/展示，不参与策略）
  formula: Record<string, string>;         // formula: token -> desc
  cask: Record<string, string>;            // cask: 同上，**分表**
}
```

- 体积估算：16,356 ×（token ~20B + desc ~55B + JSON 开销）≈ **1.0–1.2 MB**（真机实测落盘 `pref write=17ms`）。
- **必须按 kind 分表**：同名 token 在 formula 和 cask 下可能含义不同（如 `docker`），合表会串味。
- 存储：新增独立 Preference key（`brew_meta_index`），**与 `brew_live_data` 分开**。
  **硬性要求**：不得沿用 `brew_live_data` 的"整份 doc（~5 KB/条）"口径 —— 那会变成 ~80 MB 且每次整份 flush。
- 落盘 index 的唯一目的是**让首屏立刻有分类数据**（本次启动的同步还没跑完时，用上次的结果）；
  它在同步完成后整体替换。
- 目录侧：`BREW_BROWSE_KEEP` 从 200 → 全量（真机日志：`catalog 7508` formula / `5548` cask，是 family 去重后的）

### 4.2 同步策略（**已按"流量免费"简化**）

| 项 | 取值 | 说明 |
|---|---|---|
| 触发时机 | **进程启动后立即**，后台异步 | 不延迟、不阻塞首屏、不判断网络类型 |
| 频次 | **一个进程最多 1 次** | 简单的 in-flight 守卫即可，不需要任何时间常量 |
| 新鲜度 / TTL | **无**（仍不做 TTL） | 不引入“过期就重拉”的时间常量 |
| 条件请求探针 | **做**（`If-Modified-Since`，2026-09-22 从“不做”改为“做”） | **原判断“探针只省一次下载+扫描，流量免费时不值”被真机实测推翻**：省的不是流量而是**时间** —— 实测 `/api/formula.json` 的 HEAD 就要 22s、完整 GET >60s；而同步是“两个 kind 串行 await 完才写盘”，于是上游一慢，`brew_meta_index` 要 **13.3 分钟**（实测 `total=798998ms`）才落盘，而任何一次冷启动都等不到 —— 浏览页在这次冷启动里必然降级（逐条 hydrate 5~15s）。详见 §4.7。⚠ **但命中率低于当初假设**：实测 `cask.json` 的 `Last-Modified` 在 53 分钟内换了三代（§5.3），所以“按天生成”的旧描述是错的，IMS 的价值降为“同一代窗口内 0 字节” |
| 每个 kind 的等待预算 | `BREW_META_SYNC_BUDGET_MS` = 90s（**只是“先开下一个 kind”的节奏，不是超时**） | 原先 `readTimeout` = 600000（10 分钟）且两个 kind 只在末尾合写一次 —— 单个 kind 卡住就把两个结果都扣在内存里 |
| 读取超时（socket 级） | `BREW_META_READ_TIMEOUT_MS` = 600000（10 分钟），**必须远大于等待预算** | 两者写成同一个值时，下载会在预算到点那一刻被 `readTimeout` **中止**（真机实测 `ok=false text=0B download=90024ms`），“迟到落盘”就成了空话 |
| 失败处理 | 本次放弃，**下次启动自然重试** | 不做退避/重试队列；失败不影响任何页面 |
| 开关 | 无 | 回滚靠构建期常量（§8） |

失败的可见性：同步失败时页面**照旧可用**（走 §4.4 的补位路径），只少一部分分类覆盖，日志里有明确记录。

### 4.3 取数与扫描（**性能项，不简化**）

每个 kind 一次拿完，不切分：

```
GET /api/<kind>.json（gzip，Accept-Encoding 由框架自动带）
  └─ 框架自动解压 → 32.4 MB 文本（formula）/ 18.9 MB（cask）
       └─ 流式扫描（只认标识键 / desc，不建对象树）
            └─ 组装索引（~1 MB）→ 跨线程回传 → 落盘
```

两个 kind **串行**（不并发）：并发下载只会互相抢带宽，而这里不赶时间；而且串行让内存峰值只有
一份大文本（32MB）+ 一份索引。

**已定的两个实现约束（均有文档依据）**：

| 约束 | 依据 | 做法 |
|---|---|---|
| taskpool 跨线程序列化上限 16MB | `harmonyos-guides/serializable-overview.md:15` | **HTTP 下载必须在 `@Concurrent` 函数内部**，只回传索引（~1MB） |
| `maxLimit` 默认只有 5MB | `js-apis-http.md:1377` | 显式给 `BREW_META_MAX_LIMIT = 100MB`；`expectDataType` 不设 Object（那条路有 65536 字符上限） |

**连接超时与读取超时必须分开**（实测教训）：两者一开始用同一个值（180s），结果链路断掉时
整个预算被“连不上”吃满，日志只剩一句 `2300028 Operation timeout` —— 分不出是“连不上”还是“下得慢”。
现在：`BREW_META_CONNECT_TIMEOUT_MS = 10s`（建连本该是秒级的事，失败快）+ `BREW_META_TIMEOUT_MS = 600s`（读 32MB 的体）。

**抽取策略用流式扫描（不是 `JSON.parse`）**：整份解析会建一棵几万条记录的对象树，而扫描只认两个字段、
就地丢弃文本，内存是常数级；主线程大 JSON 解析也是官方点名的卡顿反模式（`faq-stability-66.md:116`）。

**标识键按 kind 传入，不能写死**（真机踩到的坑）：formula 的标识符是 `"name":"..."`，
而 **cask 的标识是 `"token":"..."`**，它的 `"name":` 是**显示名数组**（`"name":["0 A.D."]`）。
写死 `"name":` 时 cask 会 `pairs=0 skips=7761` —— 整包一条都扫不出来（详见 §4.6）。
扫描器的手写部分只有“锚点 + 转义”，正确性靠 `BREW_META_VERIFY` 的 200 条抽样对账担保。

**超时不是正确性问题**：拿不到就继续用上一份索引（落盘的那份），页面走降级路径（§4.5）。
`BREW_META_TIMEOUT_MS = 180s` —— 一次 32MB，不能按单条请求的尺度给。

### 4.4 与现有逐条 hydrate 的关系（叠加，不是替换）

> **2026-09-22 修订**：主路径的判据从"`covered > 0`"收紧为"`covered >= BREW_INDEX_MIN_TRUST` 才走索引优先"，
> 且索引可信时**不再为索引里没有的 token 发单条请求**。原因是实测那批 token 全部 404（`dl=0`）却占掉冷启动 96% 的时间。
> 见 `2026-09-22-brew-coldstart-design.md` §2。

| 情形 | 行为 |
|---|---|
| index 里有该 token | 直接用 index 的 desc 分类，**不发单条请求** |
| index 里没有（新包 / 同步未完成 / 同步失败） | **仅在索引不可信时**（`covered < BREW_INDEX_MIN_TRUST`）回落逐条 hydrate；索引可信时直接不上屏，等下一次构页（详见 `2026-09-22-brew-coldstart-design.md` §5） |

保留补位路径是**简化**（不改现有代码路径），同时保证任何同步异常都不会让页面变空。

### 4.5 分类与排序口径

- 分类：`BrewTaxonomy.categoryOf(kind, token, descIndex[token] ?? doc?.desc ?? '')`，词表与算法**不变**。
- 名次与分类大小：在**目录全量内**计算（`BrewBrowseBuilder.rankWithin` 本来就是全量内算，算法不动）；
  卡片上的「N 个包」就是全量数字。
- **硬裁切失效**：`BREW_BROWSE_LIMIT` 已删除，目录落盘也不再裁切。
  **2026-09-22 起浏览集 = 目录 ∩ 元数据索引**（索引可信时，见 §4.4 的修订）—— 不再等于目录全量：
  目录里有、而 `formula.json`/`cask.json` 里没有的 token（实测 formula 93 个）被排除在上屏之外。
- **降级**：索引**不可信**时（`covered < BREW_INDEX_MIN_TRUST`，即首次启动、同步失败、断网、扫描口径变了）
  退回 `all.slice(0, BREW_BROWSE_HYDRATE_LIMIT)` + 逐条 hydrate，**这条路与改动前一致**。
  为什么必须保留这道闸：那种情况下 `desc` 只能一条一条拉，把 1.6 万个 token
  全丢给 hydrate 会超时返回，页面反而只剩零星几条 —— 这道闸的语义是**请求预算**，不是展示上限。
- **为什么索引可信时不再 hydrate 也不会掉内容**：那批 token 实测**全部 404**（`dl=0`，一条也没上屏），
  却占掉冷启动 96% 的时间；而 `BrewMetaSync` 每次进程启动都重拉全量索引，新包在下一次构页就会出现。
  代价（上游新包晚一次构页）与回退方式见 `2026-09-22-brew-coldstart-design.md` §6.2 N1 / §11。

### 4.6 实测证据（真机 + 离线对账）

**① 真机：全量同步跑通**（`127.0.0.1:42021`，2in1，链路恢复后）：

```
meta sync: start, cached formula=0 cask=0, ts=0
meta sync [formula]: ok=true code=200 text=32367971B (connect budget 10000ms, read budget 600000ms)
                     anchor="name":  download=17779ms scan=93ms pairs=8611 skips=0  err=
meta sync [cask]:    ok=true code=200 text=18881182B ... pairs=0 skips=7761   ← 当时的 bug
meta sync: done, formula=8611 cask=0, total=21730ms, pref write=17ms
```

读到的关键数字：**32.4MB / 17.8s（≈1.8MB/s）/ 扫描 93ms / 落盘 17ms**，与“一次拿完 + 流式扫描”的预期一致。

**② cask `pairs=0` 的根因**：扫描器当时写死了 `"name":` 锚点；而 **cask 的标识键是 `"token":`**，
`"name":` 是显示名数组（`"name":["0 A.D."]`，带 `[` 而不是 `"`）→ 每个锚点都配对失败。
修法：标识键按 kind 传入（`formula → "name":` / `cask → "token":`）。

**③ 离线整包对账**（不受链路影响，脚本与 `metaScanTask` 同构）：

| kind | 文本 | 真解析 | 扫描命中 | skips | desc 不一致 | 多余 key |
|---|---|---|---|---|---|---|
| formula | 30.9 MiB | 8,611 | **8,611** | 0 | **0** | 0 |
| cask | 18.0 MiB | 7,745 | **5,100** | 2,661 | **0** | 0 |

cask 的 2,661 个 skip **全部是应该跳过的**：2,645 个是 `desc: null`（上游就没写描述，
这类包在旧代码里也无法分类、不可上屏），另外 16 个是 `variations` 里的嵌套 `desc`
（`{"variations":{"sequoia":{"desc":...}}}`，出现在对象自身 desc **之后**，被 `n >= from` 正确拒绝）。

> 落盘时 **不把 null-desc 写成空字符串**：空串会被当成“已有 desc”（`!== undefined`）而上屏成一条无标题的条目。
> 代价是这些 token 总在 `missing` 里，cask 首次浏览最多多花一轮请求预算（≤100）的 hydrate；
> 由于数据集探针能把整批 304 续期（0 字节），稳态成本可忽略。

**④ 因此补上的防御**：锚点若被反斜杠转义（`\"desc\":`，字符串内容而不是 key）则跳过。
不拦的话，从它向前找标识键会命中同一个对象，从而**用一个凭空的 desc 顶掉真 desc**
（因为 `from` 已前移，真 desc 后续会被 `n >= from` 拒掉）—— 属于“页面看着正常、内容错了”的静默错。
实测现网 **0 例**，纯防御。

### 4.7 2026-09-22 修复：索引“一个字都落不了盘”

**现象（日志打点抓到）**：每次冷启动都是 `kind=meta_index reason=missing formula=0 cask=0`，
浏览页 `reason=degraded-prefix`（逐条 hydrate）。

**证据链（真机）**

| # | 证据 | 来源 |
|---|---|---|
| 1 | `brew_meta_index` **不在** Preference 库里（`brew_catalog`/`brew_live_data`/`brew_live_dataset` 都在） | 设备 `.../preferences/HMosWorldStoreWithNet` 直接 grep |
| 2 | store 文件 mtime 停在上一次成功写入，之后多次启动**一次都没写过盘** | `stat` 该文件 |
| 3 | `meta sync: start, cached formula=0 cask=0, ts=0` 每次都有，但 **74s 内 `meta sync [formula]` 从未出现** | 轮询抓取（hilog 环形缓冲只回收到 ~12s 前，`--from` 拿不到锚点） |
| 4 | 宿主网络正常（baidu 0.12s / gitee 0.17s），但 **`/api/formula.json` HEAD 21.95s、完整 GET >60s 未完成** | `curl -w` |
| 5 | 全仓**唯一**写入者是 `sync()`；唯一删除者是 `PreferenceManager.getValue` 的 parse 失败分支 | grep |
| 6 | 让 App 跑满一轮：`meta sync [formula]` **578s** + `[cask]` **221s** = `total=798998ms`（**13.3 分钟**）后才 `pref write=17ms` 落盘。即：**不是写不了，是任何一次冷启动都等不到** | 轮询抓取（同一次运行） |

**根因（两个缺陷叠加）**

1. **串行 + 只在最后写一次**：`formula`/`cask` 串行 `await`，索引只在**两个都结束后**才 `setValue` 一次 ——
   于是第一个 kind 的 578s 把一切结果都扣在内存里。
2. **无整体截止（但 `readTimeout` 又长到 10 分钟）**：`await taskpool.execute()` 上没有任何 deadline，
   所以“等”与“不等”两个错误同时存在：写盘要等 13.3 分钟，而中途完全不可观测、也不可干预。

于是：上游慢 ⇒ 索引 13.3 分钟后才落盘 ⇒ 浏览页在这次冷启动里**必然**降级（5~15s）。
这正是“有时候近 10s”的成因。

> ⚠ **不要把它误读成“写盘慢”或“上游挂了”**：写盘 `pref write=17ms`，上游也**确实返回了 200**
> （`code=200 text=32328246B`）—— 问题全在“什么时候写”与“等不等”。

> 为何有时看着“秒开”：Discover 不用索引（内置快照 + 目录 + live 缓存，实测 37ms）；
> 而浏览页的降级又被 `brew_live_data`（1h）挡住（`session hit=189 / dl=0`，4.5s 里无真实请求）。
> **一旦 live 缓存过期或全新安装，10s 就会露出来。**

**修复**

| 改动 | 位置 | 作用 |
|---|---|---|
| 条件请求 `If-Modified-Since`（基准存 `brew_meta_stamp`，与索引分开） | `metaScanTask` | 未变时 304 + 0 字节，把 22~60s+ 的下载变成 ~1s |
| 每个 kind 独立等待预算（`BREW_META_SYNC_BUDGET_MS` = 90s，只控“何时开始下一个 kind”） | `syncKindWithBudget` | 单个 kind 卡住不再吃掉 10 分钟 |
| **迟到落盘**：预算只决定“等多久就先去开始下一个 kind”，**不丢弃结果** —— 下载在后台继续，真正结束时照常落盘 | `syncKindWithBudget` | 修掉了“硬预算会让索引永远刷不到”的新回归（实测单文件 578s，硬剪就永远拿不到表） |
| **`readTimeout` 与等待预算分开**（前者 10 分钟，后者 90s） | `BREW_META_READ_TIMEOUT_MS` | ⚠ 这是第一版实现漏掉的：两者同值时下载在 90s 被中止，根本没有“迟到的结果”可落。**由真机验证发现** |
| **每个 kind 一结束就立即落盘** | `applyKindResult` / `persistIndex` | 第二个 kind 再慢也不能把第一个的结果扣在内存里 |
| 三种结局分开表达（新表 / 304 未变 / 失败） | `MetaKindResult` | “未变”只落基准（**不重写 1MB 索引**），“失败”保留旧表并告警 —— 行为不同 |

**验证结果（2026-09-22，真机）**

| # | 判据 | 结果 |
|---|---|---|
| 1 | 索引在盘上 → 浏览页走主路径 | ✅ `kind=meta_index reason=pref formula=8613 cask=5103`；`formula_page reason=index-trusted ms=415 hydrate=0 trusted=true`；`warn 行数=0` |
| 2 | 预算到点**不中止**下载 | ✅ `reason=budget ms=90003 kind=formula` / `ms=180005 kind=cask`，且随后下载确实跑完了 |
| 3 | 迟到落盘 | ✅ `meta sync [cask]: ok=true code=200 download=416174ms` → `reason=net-200 ms=506328 pairs=5103 → 已单独落盘（不等另一个 kind）` |
| 4 | 基准写入且会被读出 | ✅ `brew_meta_stamp` 从无到有，且**自更新**（`12:36:46` → `12:59:30`）—— 证明 `Last-Modified` 确实被读出并持久化 |
| 5 | 条件请求头到底发没发 | ✅ `meta sync request, ims=[Tue, 22 Sep 2026 12:59:30 GMT] .../cask.json`（打在 `client.request` **之前**，否则慢请求要 578s 后才可见）。**基准确实被读出并附到了请求上**；配合 `Last-Modified` 每 20~30 分钟换一代，`code=200` 是合法的而非头未发 |

**过程中被实测推翻/修正的两条（都写进代码注释了）**

1. **`http.readTimeout` 不是“传输总时长”上限。**
   第一版修复把 `readTimeout` 与等待预算写成同一个值（90s），下载在 90s 被中止
   （`ok=false text=0B download=90024ms`）→ “迟到落盘”成了空话。改成 10 分钟后，
   下载确实能跨过预算继续跑完（cask 416s / 378s）。
   但要注意：它管的是**两次读取之间的间隔**，所以一个持续“细水长流”的 32MB 包可以远超 10 分钟不触发超时
   （实测 `formula.json` 在 25 分钟内**从未返回**）。这是**改动前就有的性质**，不是本次引入的。
2. **“数据按天生成”是错的。** 实测 `cask.json` 的 `Last-Modified` 在 **53 分钟内换了三代**
   （`12:36:46` → `12:59:30` → `13:30:01`）。所以 IMS 的命中率远低于设计假设，
   它的价值从“几乎总是 0 字节”降为“同一代窗口内 0 字节”。
   **但保留它仍然划算**：未命中时只是多一个被忽略的头，命中时省 18~32MB。

**诚实边界**：19:30 的日志读到过 `cached formula=8613 cask=5103`，说明它曾被成功落盘；
现在却没了。唯一可能的删除路径是 `getValue` 的 parse 失败分支（会把 key 删掉），
但当时日志已出缓冲，**未能拿到证据**。无论它是“被删”还是“flush 丢失”，
上面的结构性缺陷都成立，且修复同时改善这两种情形（每 kind 落盘 = 写入时机更早、更不易被进程退出截断）。
